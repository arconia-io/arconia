# 16. Dev UI

Date: 2026-11-20

## Status

Accepted

## Context

A Spring Boot application knows a lot about itself: its beans, the auto-configurations that matched and the ones that didn't, its request mappings, its health, its loggers, its configuration. Spring Boot makes that information available through the Actuator endpoints, which are designed for operating an application in production. They answer in JSON for tools to consume, only the health endpoint is exposed over HTTP by default, and the values of the configuration are masked by default. During development, a developer either exposes and unmasks the endpoints and reads the JSON, or relies on what the IDE shows.

Some information is hard to get at all. The effective configuration of an application comes from many sources, and finding out which properties exist, what they are set to, and where a value comes from means combining the Actuator endpoints with the documentation of each library. Nothing gives an overview of the modules an application is made of, the features they bring, and how to configure them. Arconia adds its own share of information that has no place to be shown, such as the Dev Services running for the application (see [3. Dev Services](0003-dev-services.md)), their logs, and the links to their consoles.

The first minutes with Spring Boot have a gap too. An application generated by the Spring Initializr starts successfully, and the first request from a browser returns the whitelabel error page, because no endpoint has been defined yet. Nothing says that the application works and what to do next. Later on, an error during development shows the same page, with little help in finding the cause.

The idea is inspired by the Quarkus Dev UI: when an application runs in dev mode, Quarkus serves a web interface where each extension shows its own information and tools, and a welcome page and an error page that help the developer instead of a bare status.

## Decision

Arconia provides a Dev UI: a web interface served by the application itself when it runs in dev mode (see [1. Bootstrap mode](0001-bootstrap-mode.md)). Adding one dependency is enough, with no code and no configuration.

The Dev UI has three purposes. The first is to make the information Spring Boot already has easy to navigate during development: what the Actuator endpoints provide, presented for a person instead of a tool, searchable and linked together. It reads that information from the running application and doesn't expose the Actuator endpoints or change how they are configured. The second is to show what is not easily accessible in Spring Boot: the effective configuration of the application, and an overview of its modules, with their features, properties, and documentation. The third is to help developers who are starting out. When the application has no page of its own to show, the Dev UI serves a welcome page that confirms the application is running and explains how to add a first endpoint, and error pages that describe what went wrong. They take the place of the whitelabel error page only: whatever the application defines for its root path or for its errors is left as it is. The page for a failed request shows its stack trace, so these pages follow the same rule as the rest of the Dev UI and are shown only for requests from the local machine.

These purposes describe where the Dev UI is going, and it gets there in steps. It starts with an overview of the application, its configuration properties and environment, its logs, the Dev Services, and the welcome and error pages. What the Actuator endpoints provide and the overview of the modules follow.

The content comes from the modules. Each module contributes the pages for the technology it supports, in the same way each Spring Boot module provides the connection details for its own technology, and its content appears only when the module is in use. Arconia modules contribute their own content, starting with Dev Services, and other libraries can do the same.

A module describes its content, and the Dev UI decides how it is shown. A page is one of a few kinds: a set of cards, for a handful of things with a few facts each, or a table, for what comes in large numbers. A card or a row has the same parts wherever it comes from, and the Dev UI gives each part its place, so that the pages of different modules look and work alike, and a module has no frontend to write. Pages about one subject are gathered in a section of the navigation, such as the one for configuration, and the sections are the ones the Dev UI defines.

The API that modules use to contribute pages is separate from the server that shows them. A module depends on the API alone, as an optional dependency, describes its pages, and supplies their content when asked, without knowing how they are served. It contributes a page only when the API is on the class path.

The Dev UI is a tool for the developer working on the application, on their own machine. It is a development dependency, declared like the Dev Services and left out of the packaged application, and it accepts requests from the local machine only unless configured otherwise. It is not a way to administer an application remotely or in production, where the Actuator endpoints and an observability platform remain the tools to use.

It is built for the servlet stack only (see [6. Reactive stack](0006-reactive-stack.md)). It stays incubating after the first GA release of Arconia (see [9. API stability markers](0009-api-stability-markers.md)), including the API that modules use to contribute content, so that it can keep changing as it is tried out.

## Consequences

A developer gets an overview of the running application by opening a page, and a new application answers its first request with guidance instead of an error.

The Dev UI is one more thing each module has to maintain: when a module gains a feature worth showing, its Dev UI content follows. The information it reads from Spring Boot has to keep up with each Spring Boot release.

The application behaves differently in dev mode where it has no page of its own: a request to an undefined root path or a failing request shows a Dev UI page instead of the whitelabel error page seen in production.

Reactive applications and applications without a web server have no Dev UI. Libraries contributing content build on an API that may change in any release.
