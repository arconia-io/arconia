= OpenTelemetry Semantic Conventions
:page-aliases: observation:semantic-conventions/opentelemetry.adoc

The Spring portfolio provides built-in instrumentation based on the Micrometer APIs. Arconia lets you configure your applications to export telemetry data adopting the https://opentelemetry.io/docs/specs/semconv/[OpenTelemetry Semantic Conventions] instead of the default Micrometer conventions.

OpenTelemetry Semantic Conventions are the standard for cloud-native observability and are supported by a wide range of backends, from on-premises to cloud solutions. Arconia provides Dev Services for OpenTelemetry backends you can use during development and testing. Check out the xref:dev-services:index.adoc[Dev Services] documentation for more details.

== Getting Started

Add the Arconia OpenTelemetry Semantic Conventions dependency to your project. The module auto-activates when present on the classpath.

[tabs]
======
Gradle::
+
[source,groovy]
----
dependencies {
  implementation 'io.arconia:arconia-opentelemetry-semantic-conventions'
}
----

Maven::
+
[source,xml]
----
<dependency>
    <groupId>io.arconia</groupId>
    <artifactId>arconia-opentelemetry-semantic-conventions</artifactId>
</dependency>
----
======

Your application also needs OpenTelemetry configured for traces and metrics export, using either the xref:opentelemetry:index.adoc[Arconia OpenTelemetry Spring Boot Starter] or the https://docs.spring.io/spring-boot/reference/actuator/observability.html[Spring Boot OpenTelemetry support] (`spring-boot-starter-opentelemetry`). The recommended approach is the Arconia OpenTelemetry Spring Boot Starter:

[tabs]
======
Gradle::
+
[source,groovy]
----
dependencies {
  implementation 'io.arconia:arconia-spring-boot-starter-opentelemetry'
}
----

Maven::
+
[source,xml]
----
<dependency>
    <groupId>io.arconia</groupId>
    <artifactId>arconia-spring-boot-starter-opentelemetry</artifactId>
</dependency>
----
======

If you use one of the available xref:dev-services:index.adoc[OpenTelemetry Dev Services] during development or testing, Arconia will configure OpenTelemetry automatically to export logs, metrics, and traces to the specific service based on the OpenTelemetry Semantic Conventions.

== Stability

The OpenTelemetry Semantic Conventions module only adopts conventions declared stable by OpenTelemetry: the JVM metrics, the HTTP server and client spans and metrics, and the `error.type` attribute. The only exception is the `jvm.gc.cause` attribute of the `jvm.gc.duration` metric, which is still in development but kept because it tells garbage collection pauses and concurrent phases apart (see <<_jvm,JVM>>).

The OpenTelemetry Semantic Conventions for <<_generative_ai,Generative AI>> are still in development, and they are provided by a separate module.

=== Known Deviations

Some differences from the stable conventions come from the Micrometer instrumentation and are tracked upstream:

* The `jvm.cpu.time` metric is reported in nanoseconds instead of seconds (https://github.com/micrometer-metrics/micrometer/issues/7703[micrometer#7703]).
* The `jvm.memory.used`, `jvm.memory.committed`, `jvm.memory.limit`, `jvm.thread.count`, `jvm.class.count`, and `jvm.cpu.count` metrics are exported as gauges instead of non-monotonic sums (https://github.com/micrometer-metrics/micrometer/issues/7432[micrometer#7432]).
* The `jvm.thread.count` metric doesn't have the `jvm.thread.daemon` attribute (https://github.com/micrometer-metrics/micrometer/issues/7702[micrometer#7702]).
* Spans started without a parent outside of an HTTP request, such as the span of a database connection opened at application startup, get the `Ok` status when they end without an error, instead of being left unset, because the Micrometer Tracing OpenTelemetry bridge sets it (https://github.com/micrometer-metrics/tracing/issues/890[tracing#890]). The spans of HTTP requests and their child spans aren't affected.
* Attribute values are always strings, also for attributes defined as numbers, such as `http.response.status_code` and `server.port` (https://github.com/micrometer-metrics/micrometer/issues/7433[micrometer#7433]).

== Histograms

The duration and token usage metrics defined by the OpenTelemetry Semantic Conventions are histograms. As in Spring Boot, their buckets are not published by default, to keep the number of time series low: only the count, sum, and maximum are exported, which is enough for throughput and average values. To compute percentiles, enable the histogram buckets for the metrics you need.

You can use the bucket boundaries advised by the OpenTelemetry Semantic Conventions with the Spring Boot `management.metrics.distribution.slo` properties.

[source,yaml]
----
management:
  metrics:
    distribution:
      slo:
        http.server.request.duration: 5ms,10ms,25ms,50ms,75ms,100ms,250ms,500ms,750ms,1000ms,2500ms,5000ms,7500ms,10000ms
----

[cols="2,3"]
|===
|Metric |Advised Bucket Boundaries

|`http.server.request.duration`, `http.client.request.duration`
|`5ms,10ms,25ms,50ms,75ms,100ms,250ms,500ms,750ms,1000ms,2500ms,5000ms,7500ms,10000ms`

|`jvm.gc.duration`
|`10ms,100ms,1000ms,10000ms`

|`gen_ai.client.operation.duration`
|`10ms,20ms,40ms,80ms,160ms,320ms,640ms,1280ms,2560ms,5120ms,10240ms,20480ms,40960ms,81920ms`

|`gen_ai.client.token.usage`
|`1,4,16,64,256,1024,4096,16384,65536,262144,1048576,4194304,16777216,67108864`
|===

Alternatively, you can publish exponential histograms, which adapt their buckets to the recorded values and don't need any boundaries. With the xref:opentelemetry:index.adoc[Arconia OpenTelemetry Spring Boot Starter], select the exponential aggregation and enable the histograms with the Spring Boot `management.metrics.distribution.percentiles-histogram` properties.

[source,yaml]
----
arconia:
  otel:
    metrics:
      exporter:
        histogram-aggregation: base2-exponential-bucket-histogram
management:
  metrics:
    distribution:
      percentiles-histogram:
        http.server.request.duration: true
----

== JVM

Provides semantic conventions for JVM metrics, following the stable https://opentelemetry.io/docs/specs/semconv/runtime/jvm-metrics/[OpenTelemetry Semantic Conventions for JVM] specification:

* Memory metrics
* Thread metrics
* Class loader metrics
* CPU/processor metrics.

Semantic Conventions for JVM are based on the support provided by the https://micrometer.io[Micrometer Metrics] project, extended by Arconia to support additional stable conventions.

The `jvm.gc.duration` metric replaces both the `jvm.gc.pause` and `jvm.gc.concurrent.phase.time` metrics from Micrometer, so it covers both garbage collection pauses and concurrent phases. The `jvm.gc.name` and `jvm.gc.cause` attributes tell them apart: for example, `G1 Young Generation` pauses versus `G1 Concurrent GC` phases (with cause `No GC`), or `ZGC Pauses` versus `ZGC Cycles`.

The Micrometer `jvm.threads.live` metric is not published, since the `jvm.thread.count` metric replaces it: summed over the `jvm.thread.state` attribute, it counts the same live platform threads. The other Micrometer JVM metrics without an equivalent in the OpenTelemetry Semantic Conventions, such as `jvm.threads.daemon` and `jvm.threads.peak`, are kept.

.JVM Configuration Properties
|===
|Property |Default |Description

|	`arconia.observations.conventions.opentelemetry.jvm.enabled`
|	`true`
|	Whether to enable JVM semantic conventions.
|===

== HTTP

Provides semantic conventions for HTTP server and client request observations, following the stable https://opentelemetry.io/docs/specs/semconv/http/[OpenTelemetry Semantic Conventions for HTTP] specification.

Spans of requests whose response status code signals an error get the `Error` status even when no exception was thrown: `5xx` for HTTP servers, `4xx` and `5xx` for HTTP clients. It requires the Micrometer Tracing OpenTelemetry bridge, which both the Arconia OpenTelemetry Spring Boot Starter and `spring-boot-starter-opentelemetry` include.

=== HTTP Server

Activated when the application is a servlet-based web application. Semantic Conventions for HTTP Server are based on the support provided by the https://spring.io/projects/spring-framework[Spring Framework] project, extended by Arconia to support additional stable conventions.

=== HTTP Client

Activated for the `RestClient` and `RestTemplate` instances built from the builders auto-configured by Spring Boot. The requests are reported with the `http.client.request.duration` metric and spans named after the request method, such as `GET`. The full URL of the request is recorded as `url.full`, with the credentials and the values of sensitive query parameters replaced by `REDACTED`.

The `outcome` and `uri` attributes from Spring Framework are kept, since the OpenTelemetry Semantic Conventions don't define a stable equivalent for them. The `uri` attribute holds the path of the URI template used for the request, such as `/users/\{id}`, and lets you break down the client metrics by endpoint.

=== Configuration Properties

.HTTP Configuration Properties
|===
|Property |Default |Description

|	`arconia.observations.conventions.opentelemetry.http.enabled`
|	`true`
|	Whether to enable HTTP semantic conventions for HTTP servers and clients.

|	`arconia.observations.conventions.opentelemetry.http.capture-url-query`
|	`false`
|	Whether to capture the URL query string in the HTTP server observations. Disabled by default due to potential PII sensitivity. The HTTP client observations always include it in `url.full`.

|	`arconia.observations.conventions.opentelemetry.http.sensitive-query-parameters`
|	`AWSAccessKeyId`, `Signature`, `X-Amz-Signature`, `X-Amz-Credential`, `X-Amz-Security-Token`, `sig`, `X-Goog-Signature`
|	Query parameters whose values are replaced by `REDACTED` in the URL query string of the HTTP server and client observations, matched case-sensitively. Setting it replaces the default list, and an empty list disables the redaction.
|===

== Errors

Records the stable `error.type` attribute on every observation ending in an error, following the https://opentelemetry.io/docs/specs/semconv/general/recording-errors/[OpenTelemetry Semantic Conventions for recording errors]. The attribute holds the fully qualified class name of the error, unless the convention for the observation already sets a more specific value, such as the status code of HTTP responses signaling an error (`5xx` for servers, `4xx` and `5xx` for clients), and it's recorded on both the span and the metrics of the observation. It's not recorded for successful operations, so the `none` value Spring Framework sets on successful HTTP server requests is removed.

.Errors Configuration Properties
|===
|Property |Default |Description

|	`arconia.observations.conventions.opentelemetry.error.enabled`
|	`true`
|	Whether to enable error semantic conventions, recording the `error.type` attribute on observations ending in an error.
|===

== Database

Activated when the https://jdbc-observations.github.io/datasource-micrometer/docs/current/docs/html/[Datasource Micrometer] dependencies are added to the project. They automatically instrument all `DataSource` beans in your Spring Boot application, generating metrics and traces for database queries executed via JDBC following the stable https://opentelemetry.io/docs/specs/semconv/database/[OpenTelemetry Semantic Conventions for Database]. Arconia manages the versions of the dependencies for you.

[tabs]
======
Gradle::
+
[source,groovy]
----
dependencies {
  implementation 'net.ttddyy.observation:datasource-micrometer-spring-boot'
  implementation 'net.ttddyy.observation:datasource-micrometer-opentelemetry'
}
----

Maven::
+
[source,xml]
----
<dependency>
    <groupId>net.ttddyy.observation</groupId>
    <artifactId>datasource-micrometer-spring-boot</artifactId>
</dependency>
<dependency>
    <groupId>net.ttddyy.observation</groupId>
    <artifactId>datasource-micrometer-opentelemetry</artifactId>
</dependency>
----
======

Refer to the https://jdbc-observations.github.io/datasource-micrometer/docs/current/docs/html/[Datasource Micrometer documentation] for configuration options and more details.

=== Known Deviations

The Datasource Micrometer instrumentation currently deviates from the OpenTelemetry Semantic Conventions for Database in the following ways:

* Failed queries don't get the `db.response.status_code` attribute, and the `db.client.operation.duration` metric doesn't get the `error.type` attribute. Arconia records `error.type` on the spans (see <<_errors,Errors>>).
* The `server.port` attribute is recorded also for the default port of the database, and as `-1` when the connection URL doesn't specify a port. The `db.client.operation.duration` metric also gets `network.peer.address` and `network.peer.port` from the connection URL.
* The `db.client.operation.duration` metric gets the `db.query.text` attribute, which the conventions make opt-in for metrics because of its potentially high cardinality.
* The `db.query.summary` attribute and the span name of `INSERT ... VALUES` queries wrongly include a `SELECT` operation, and `db.operation.name` uses underscores for operations made of several words, such as `CREATE_TABLE`, instead of matching the query summary.
* Each query is also recorded with the `jdbc.query` metric from Micrometer, in addition to `db.client.operation.duration`.

=== Features

* Chat model spans with full parameter tracking (e.g., temperature, max tokens, penalties, stop sequences).
* Embedding model spans with dimension tracking.
* Tool execution spans.
* Chat client spans, reported as agent invocations (`invoke_agent`) with conversation ID tracking via chat memory.
* Operation duration metrics (`gen_ai.client.operation.duration`) for chat, embedding, and image model calls.
* Token usage metrics (`gen_ai.client.token.usage`).
* Input/output message content, captured as span attributes, span events, or log events.

Model calls, embeddings, tool executions, and chat client calls ending in an error get the `error.type` attribute when the <<_errors,error conventions>> are active.

=== Content Capturing

Model calls and tool executions can carry sensitive data, so capturing their content is opt-in. Three properties enable it: `capture-message-content` for the input and output messages of model calls, `capture-tool-definitions` for the definitions of the tools available to the model, and `capture-tool-call-content` for the arguments and result of tool executions.

The `inference-content-destination` property decides where the captured messages and tool definitions of a model call are recorded:

* `span-attributes` (default): as attributes of the model call span.
* `log-events`: in a `gen_ai.client.inference.operation.details` event exported through the OpenTelemetry Logs API, as defined by the OpenTelemetry Semantic Conventions. The event carries the attributes of the model call span and the content in structured form, and it's correlated with the span. It's exported together with the other application logs, whether OpenTelemetry is configured by the xref:opentelemetry:index.adoc[Arconia OpenTelemetry Spring Boot Starter] or by the Spring Boot OpenTelemetry support.
* `span-events`: in a `gen_ai.client.inference.operation.details` event attached to the model call span. The OpenTelemetry Semantic Conventions don't define this option, but it suits backends that display span events alongside the trace.

The arguments and result of tool executions are always recorded as attributes of the tool execution span, the only option the OpenTelemetry Semantic Conventions define for them. The same goes for the input and output messages of a chat client call, recorded on the agent invocation span: they are recorded only with the `span-attributes` destination, since with the other destinations the model calls of the chat client already carry them in their events.
