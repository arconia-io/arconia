= Ollama Dev Service
:service-name: ollama

A service providing an https://ollama.com[Ollama] model inference service for development and testing purposes.

It works with Spring Boot libraries that support Ollama, including:

* https://spring.io/projects/spring-ai[Spring AI] (Ollama, OpenAI)

[NOTE]
====
If a native Ollama connection is detected, for example, if you're already running the Ollama application on your laptop, the Ollama Dev Service will not start a container and the native service will be used instead. The detection targets the URL configured via `spring.ai.ollama.base-url`, or `http://localhost:11434` if not set. You can force the use of the container via the `arconia.dev.services.ollama.ignore-native-service` property.
====

== Running the Application

include::partial$running-application.adoc[]

By default, when running the application in dev mode, multiple applications running simultaneously use the same Ollama Dev Service: the application connects to a running Ollama Dev Service started by another application if available, or else starts its own that other applications can discover in turn. This requires the Spring AI Ollama module on the classpath: applications using only the OpenAI-compatible integration always start their own container. To always start a container for the application alone, set the `arconia.dev.services.{service-name}.reuse-strategy` property to `none`. Learn more about xref:index.adoc#_reusing_dev_services[Reusing Dev Services].

== Configuring the Dev Service

You can configure the Dev Service via configuration properties.

|===
|Property |Default |Description

| `arconia.dev.services.{service-name}.enabled`
| `true`
| Whether the dev service is enabled.

| `arconia.dev.services.{service-name}.image-name`
| `ollama/ollama`
| Full name of the container image used in the dev service.

| `arconia.dev.services.{service-name}.environment`
| `{}`
| Environment variables to set in the service.

| `arconia.dev.services.{service-name}.network-aliases`
| `[]`
| Network aliases to assign to the dev service container.

| `arconia.dev.services.{service-name}.port`
| `0`
| Fixed port for exposing the Ollama inference service port to the host. When it's 0 (default), a random available port is assigned dynamically.

| `arconia.dev.services.{service-name}.resources`
| `[]`
| Resources from the classpath or host filesystem to copy into the container. They can be files or directories that will be copied to the specified destination path inside the container at startup and are immutable (read-only).

| `arconia.dev.services.{service-name}.reuse-strategy`
| `framework`
| Strategy for reusing a running container for the dev service instead of starting a new one. With `framework`, the dev service is discoverable by other applications, and the application connects to an existing dev service if available. With `testcontainers`, the container is kept running across application restarts, relying on the Testcontainers reusable containers feature, which must be enabled in the `~/.testcontainers.properties` file; such containers are not stopped automatically and must be cleaned up manually. Only applicable in dev mode.

| `arconia.dev.services.{service-name}.startup-timeout`
| `120s`
| Maximum waiting time for the service to start.

| `arconia.dev.services.{service-name}.volumes`
| `[]`
| Files or directories to mount from the host filesystem into the container. They are mounted at the specified destination path inside the container at startup and are mutable (read-write). Changes in either the host or the container will be immediately reflected in the other.

| `arconia.dev.services.{service-name}.ignore-native-service`
| `false`
| Whether to ignore an Ollama native service available on the host, but always use the container instead.

| `arconia.dev.services.{service-name}.models`
| `[]`
| Names of the models to pull into the dev service once the container is ready, such as `qwen3:0.6b`. They are pulled in the order they are declared. When empty (default), no model is pulled.

| `arconia.dev.services.{service-name}.openai-compatibility`
| `true`
| Whether to configure the Spring AI OpenAI client to use the OpenAI-compatible API exposed by the dev service, when the Spring AI OpenAI module is on the classpath.
|===

== Pulling Models

By default, the Ollama Dev Service starts without any model. You can have one or more models pulled automatically once the container is ready via the `models` property. They are pulled in the order they are declared.

[source,yaml]
----
arconia:
  dev:
    services:
      ollama:
        models:
          - ministral-3:3b
          - nomic-embed-text:v1.5
----

[NOTE]
====
The first pull downloads the entire model and can take a long time. Consider setting the `reuse-strategy` property to `testcontainers` so that you don't pay that cost at every application restart. The container is then no longer discoverable by other applications.

Only containers started by the application are affected. When the application connects to a container started by another application, its models are left untouched.
====

== Spring AI OpenAI Compatibility

When the Spring AI OpenAI module is on the classpath, the Ollama Dev Service automatically configures the OpenAI client to use the Ollama-compatible API endpoint. The `spring.ai.openai.base-url` and `spring.ai.openai.api-key` properties are set dynamically, pointing to the Ollama container when available or to the native Ollama service otherwise.

[NOTE]
====
While the Ollama Dev Service is enabled, these properties take precedence over any user-defined configuration, and the API key is set to `ollama`.

If you want your application to use a real OpenAI endpoint in dev or test mode, opt out of the compatibility layer via `arconia.dev.services.ollama.openai-compatibility=false`. The Ollama Dev Service keeps running and your `spring.ai.openai.*` configuration is left untouched, which is useful when you use Ollama and OpenAI side by side. Disabling the Ollama Dev Service altogether via `arconia.dev.services.ollama.enabled=false` also works.
====
