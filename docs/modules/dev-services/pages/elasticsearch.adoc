= Elasticsearch Dev Service
:service-name: elasticsearch

A service providing an https://www.elastic.co/elasticsearch[Elasticsearch] search and analytics engine for development and testing purposes.

It works with Spring Boot libraries that support Elasticsearch, including:

* https://spring.io/projects/spring-ai[Spring AI] (Vector Store)
* https://spring.io/projects/spring-data-elasticsearch[Spring Data Elasticsearch]

== Running the Application

include::partial$running-application.adoc[]

By default, each application starts its own Elasticsearch Dev Service. To let multiple applications running simultaneously in dev mode use the same one, set the `arconia.dev.services.{service-name}.reuse-strategy` property to `framework`: the application connects to a running Elasticsearch Dev Service started by another application if available, or else starts its own that other applications can discover in turn. The applications using the same Dev Service must use the same password. Learn more about xref:index.adoc#_reusing_dev_services[Reusing Dev Services].

== Configuring the Dev Service

You can configure the Dev Service via configuration properties.

|===
|Property |Default |Description

| `arconia.dev.services.{service-name}.enabled`
| `true`
| Whether the dev service is enabled.

| `arconia.dev.services.{service-name}.image-name`
| `docker.elastic.co/elasticsearch/elasticsearch`
| Full name of the container image used in the dev service.

| `arconia.dev.services.{service-name}.environment`
| `{}`
| Environment variables to set in the service.

| `arconia.dev.services.{service-name}.network-aliases`
| `[]`
| Additional hostnames the dev service container is reachable by on the shared network, next to the name of the dev service. Only applicable when the shared network is enabled.

| `arconia.dev.services.{service-name}.port`
| `0`
| Fixed port for exposing the Elasticsearch database port to the host. When it's 0 (default), a random available port is assigned dynamically.

| `arconia.dev.services.{service-name}.resources`
| `[]`
| Resources from the classpath or host filesystem to copy into the container. They can be files or directories that will be copied to the specified destination path inside the container at startup and are immutable (read-only).

| `arconia.dev.services.{service-name}.reuse-strategy`
| `none`
| Strategy for reusing a running container for the dev service instead of starting a new one. With `framework`, the dev service is discoverable by other applications, and the application connects to an existing dev service if available. With `testcontainers`, the container is kept running across application restarts, relying on the Testcontainers reusable containers feature, which must be enabled in the `~/.testcontainers.properties` file; such containers are not stopped automatically and must be cleaned up manually. Only applicable in dev mode.

| `arconia.dev.services.{service-name}.startup-timeout`
| `30s`
| Maximum waiting time for the service to start, counted from the container start.

| `arconia.dev.services.{service-name}.volumes`
| `[]`
| Files or directories to mount from the host filesystem into the container. They are mounted at the specified destination path inside the container at startup and are mutable (read-write). Changes in either the host or the container will be immediately reflected in the other.

== Using SSL

Elasticsearch only accepts HTTPS connections in its default configuration: it generates a certificate of its own at startup and serves HTTPS with it. Since the application has no way to trust that certificate, the Dev Service serves plain HTTP by default, and the application connects to it with the `elastic` user and the password Testcontainers sets.

To connect over HTTPS instead, as an application configured for a real Elasticsearch cluster does, set the `arconia.dev.services.{service-name}.ssl.enabled` property to `true`. With no certificate configured, Elasticsearch keeps the one it generates (the protocol and options of the `ssl` properties don't apply to it), and the application trusts it through the Spring Boot service connection, which extracts the certificate authority from the container, as described in https://docs.spring.io/spring-boot/reference/testing/testcontainers.html#testing.testcontainers.service-connections.ssl[Spring Boot's documentation]. An application connecting to a container started by another application (see xref:index.adoc#_reusing_dev_services[Reusing Dev Services]) reads the certificate authority from that container the same way.

[source,yaml,subs="attributes+"]
----
arconia:
  dev:
    services:
      {service-name}:
        ssl:
          enabled: true
----

To have Elasticsearch serve HTTPS with a certificate of yours instead, configure the certificate and private key it presents.
