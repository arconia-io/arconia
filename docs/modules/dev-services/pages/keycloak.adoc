= Keycloak Dev Service
:service-name: keycloak

A service providing a https://www.keycloak.org[Keycloak] identity and access management server for development and testing purposes.

It configures the Spring Security libraries on the classpath automatically so that a Spring Boot application needs no OAuth2 configuration to get started:

* https://docs.spring.io/spring-security/reference/servlet/oauth2/login/index.html[Spring Security OAuth2 Client], to log users in.
* https://docs.spring.io/spring-security/reference/servlet/oauth2/resource-server/index.html[Spring Security OAuth2 Resource Server], to validate access tokens.

The Dev Service imports a realm named `arconia` with a confidential client (id `arconia-app`, secret `arconia-secret`), and two users:

[cols="1,1,1"]
|===
|Username |Password |Realm Roles

| `isabella`
| `isabella`
| `admin`, `user`

| `bjorn`
| `bjorn`
| `user`
|===

The application logs show the URLs of the Keycloak Admin Console, where you can log in as `arconia`/`arconia`, and of the realm's OpenID Connect issuer.

[source,logs]
----
...i.a.d.s.startup  : Dev Service 'keycloak' is ready in container <container-id> (quay.io/keycloak/keycloak, reuse-strategy: framework)
...i.a.d.s.startup  : Dev Service 'keycloak' links: Keycloak Admin Console: http://localhost:<port>/admin, OpenID Connect Issuer: http://localhost:<port>/realms/arconia
----

To reach the server from your own code, inject the `KeycloakConnectionDetails` bean, which provides the server URL, the realm, and the issuer URI.

== Logging Users In

When Spring Security's OAuth2 Client is on the classpath, the Dev Service registers the client as a `ClientRegistrationRepository` bean, with registration id `keycloak`. Start the login at `/oauth2/authorization/keycloak` and sign in as one of the users above.

The client is configured with the `client.*` properties of the Dev Service, which also declare it in the realm, so the two always match. Your `spring.security.oauth2.client` properties are not used while the Dev Service is active, so you can keep your production configuration as it is.

The Dev Service's `ClientRegistrationRepository` replaces any your application defines, so production configuration never gets in the way in dev. To keep your own instead, set `arconia.dev.services.{service-name}.client.enabled=false`.

== Protecting a Resource Server

When Spring Security's OAuth2 Resource Server is on the classpath, the Dev Service configures it to validate the tokens issued by the realm, taking precedence over your own configuration. It sets these `spring.security.oauth2.resourceserver.jwt` properties:

* `issuer-uri` and `jwk-set-uri`, pointing at the realm.
* `jws-algorithms`, set to `RS256`.
* `audiences`, cleared, since the tokens can't carry the audience your production identity provider adds.

Properties describing how your application reads a token, such as `authorities-claim-name`, are left as you configured them. To use your own configuration instead, set `arconia.dev.services.{service-name}.resource-server.enabled=false`.

The client allows the password grant, so you can get a token without a browser, using the issuer URI from the application logs:

[tabs]
======
HTTPie::
+
[source,shell]
----
http --form <issuer-uri>/protocol/openid-connect/token \
  grant_type=password client_id=arconia-app client_secret=arconia-secret \
  username=isabella password=isabella
----

curl::
+
[source,shell]
----
curl -s <issuer-uri>/protocol/openid-connect/token \
  -d grant_type=password -d client_id=arconia-app -d client_secret=arconia-secret \
  -d username=isabella -d password=isabella
----
======

Send the `access_token` from the response as `Authorization: Bearer <token>`.

== Customizing Users and Roles

[source,yaml]
----
arconia:
  dev:
    services:
      keycloak:
        realm:
          users:
            alice:
              password: alice-password
              roles: [editor, reader]
            bob:
              password: bob-password
              roles: [reader]
----

Usernames must be lower-case, and each user gets the email address `<username>@arconia.io` and its capitalized username as first and last name, since Keycloak requires them to issue tokens. The realm roles are the ones the users hold.

Configuring users replaces the default users.

== Importing Realms

For anything the generated realm doesn't cover, import your own realm files from the classpath or the filesystem:

[source,yaml]
----
arconia:
  dev:
    services:
      keycloak:
        realm:
          import-paths: classpath:keycloak/realm.json
        client:
          id: my-app
          secret: my-secret
----

The realm name is read from the file, which must also declare the client configured in `client.*`. Imported realms take precedence: `realm.users` only applies to the generated realm.

A realm file holds either a single realm or a list of realms, in the formats https://www.keycloak.org/server/importExport[Keycloak exports]. Keycloak reads a file named `<realm>-realm.json` as that single realm, so name a file that way only if it declares that realm. Import several files by listing them:

[source,yaml]
----
arconia:
  dev:
    services:
      keycloak:
        realm:
          import-paths:
            - classpath:keycloak/dukes-realm.json
            - classpath:keycloak/beans-realm.json
          name: beans
----

When the files declare several realms, `realm.name` selects the one the application connects to and that the `KeycloakConnectionDetails` describe. It defaults to the first realm declared, skipping `master`. The application logs list the OpenID Connect issuer of every imported realm.

An export of all realms also includes `master`. Importing it is fine: Keycloak still creates the Dev Service administrator in it, so the imported `master` realm must not already have a user named like `admin-username`. That happens with an export taken from the Dev Service container itself: either set another `admin-username` or drop `master` from the file.

A multitenant application, with a realm for each tenant, typically configures Spring Security itself to pick the realm from the request. Keep its own configuration by disabling the `client` and `resource-server` wiring of the Dev Service, and give the Dev Service a fixed `port` if the issuer URIs the application resolves are fixed too:

[source,yaml]
----
arconia:
  dev:
    services:
      keycloak:
        port: 8080
        realm:
          import-paths: file:../keycloak/realms.json
        client:
          enabled: false
        resource-server:
          enabled: false
----

[WARNING]
====
The generated realm is meant for a throwaway container: it doesn't require SSL, accepts any redirect URI, and its credentials are published in this documentation. Don't use a realm exported from it anywhere else.
====

== Sharing Keycloak Across Applications

By default, in dev mode, an application connects to a Keycloak Dev Service started by another application if available, or else starts its own. Give every application sharing it the same `realm.*` configuration, so the realm is the same whichever starts first. To always start a container for the application alone, set `arconia.dev.services.{service-name}.reuse-strategy` to `none`. Learn more about xref:index.adoc#_reusing_dev_services[Reusing Dev Services].

== Calling Back into the Application

The login flow needs no special networking, since the browser performs the redirects. If Keycloak has to call your application, as for https://openid.net/specs/openid-connect-backchannel-1_0.html[OpenID Connect Back-Channel Logout], list its port under `host-accessible-ports`, and use `http://host.testcontainers.internal:<port>` as the URL in the realm.

[source,yaml]
----
arconia:
  dev:
    services:
      keycloak:
        host-accessible-ports:
          - 8080
----

== Configuring the Dev Service

You can configure the Dev Service via configuration properties.

|===
|Property |Default |Description

| `arconia.dev.services.{service-name}.enabled`
| `true`
| Whether the dev service is enabled.

| `arconia.dev.services.{service-name}.image-name`
| `quay.io/keycloak/keycloak`
| Full name of the container image used in the dev service.

| `arconia.dev.services.{service-name}.environment`
| `{}`
| Environment variables to set in the service.

| `arconia.dev.services.{service-name}.network-aliases`
| `[]`
| Additional hostnames the dev service container is reachable by on the shared network, next to the name of the dev service. Only applicable when the shared network is enabled.

| `arconia.dev.services.{service-name}.port`
| `0`
| Fixed port for exposing the Keycloak HTTP port to the host. When it's 0 (default), a random available port is assigned dynamically.

| `arconia.dev.services.{service-name}.resources`
| `[]`
| Resources from the classpath or host filesystem to copy into the container. They can be files or directories that will be copied to the specified destination path inside the container at startup and are immutable (read-only).

| `arconia.dev.services.{service-name}.reuse-strategy`
| `framework`
| Strategy for reusing a running container for the dev service instead of starting a new one. Only applicable in dev mode.

| `arconia.dev.services.{service-name}.startup-timeout`
| `2m`
| Maximum waiting time for the service to start, counted from the container start.

| `arconia.dev.services.{service-name}.volumes`
| `[]`
| Files or directories to mount from the host filesystem into the container. They are mounted at the specified destination path inside the container at startup and are mutable (read-write). Changes in either the host or the container will be immediately reflected in the other.

| `arconia.dev.services.{service-name}.admin-username`
| `arconia`
| Username of the Keycloak administrator, used to access the Admin Console.

| `arconia.dev.services.{service-name}.admin-password`
| `arconia`
| Password of the Keycloak administrator, used to access the Admin Console.

| `arconia.dev.services.{service-name}.realm.name`
| `arconia`
| Name of the generated realm, or the realm the application connects to among the imported ones. Defaults to the first imported realm other than `master`.

| `arconia.dev.services.{service-name}.realm.import-paths`
| `[]`
| Paths to Keycloak realm files to import instead of generating a realm, resolved from the classpath or the host filesystem. Each can be prefixed with `classpath:` or `file:`, and declares a single realm or a list of realms, as exported by Keycloak.

| `arconia.dev.services.{service-name}.realm.users`
| `isabella`, `bjorn`
| Users of the generated realm, by username, each with a `password` and the realm `roles` it holds.

| `arconia.dev.services.{service-name}.client.enabled`
| `true`
| Whether the dev service declares the client in the generated realm and registers it with Spring Security.

| `arconia.dev.services.{service-name}.client.id`
| `arconia-app`
| Identifier of the client. With an imported realm, the realm file must declare it.

| `arconia.dev.services.{service-name}.client.secret`
| `arconia-secret`
| Secret of the client.

| `arconia.dev.services.{service-name}.client.registration-id`
| `keycloak`
| Identifier of the Spring Security client registration, as used in the login URL `/oauth2/authorization/\{registration-id}`.

| `arconia.dev.services.{service-name}.resource-server.enabled`
| `true`
| Whether the resource server is configured to validate the tokens issued by the dev service.

| `arconia.dev.services.{service-name}.host-accessible-ports`
| `[]`
| Ports on the host that Keycloak can reach from inside its container, such as for OpenID Connect Back-Channel Logout.
|===
