= Arconia Dev Services

Arconia Dev Services streamline your development workflow by automatically provisioning external services your application depends on during development and testing. No manual setup is required.

Need a database, message broker, or other infrastructure components for your application? Add the corresponding Dev Service dependency to your project. When you run your application or tests, the required services start automatically as OCI containers and are seamlessly wired into your application. Zero additional code or configuration needed.

Built on https://testcontainers.com[Testcontainers] and https://docs.spring.io/spring-boot/reference/features/dev-services.html#features.dev-services.testcontainers[Spring Boot's Testcontainers support], Arconia Dev Services provide a great developer experience by eliminating the friction of manually setting up and managing services in your development environment.

[NOTE]
====
Dev Services are designed exclusively for development and testing workflows. Declared as development/test-only dependencies, they are excluded from production builds and have zero impact on your production deployments.
====

== How It Works

When Arconia Dev Services are detected while the application is running in xref:ROOT:core-features/bootstrap-mode.adoc[dev or test mode], the framework:

1. Starts the container: Launches an OCI container for the required service using Testcontainers.
2. Configures the connection: Sets up connection properties (URLs, credentials, ports).
3. Wires the service: Integrates the service into your application context using Spring Boot's Service Connection mechanism.
4. Manages the lifecycle: Handles container startup, shutdown, and cleanup.

This happens transparently without requiring any code or configuration.

== Quick Start

You need a container runtime, such as https://podman-desktop.io[Podman] or https://www.docker.com[Docker], installed and running. Then get started with Arconia Dev Services in three simple steps:

1. Add the dependency for your required service (e.g., PostgreSQL):
+
[tabs]
======
Gradle::
+
[source,groovy]
----
dependencies {
    testAndDevelopmentOnly 'io.arconia:arconia-dev-services-postgresql'
}
----

Maven::
+
[source,xml]
----
<dependency>
    <groupId>io.arconia</groupId>
    <artifactId>arconia-dev-services-postgresql</artifactId>
    <scope>runtime</scope>
    <optional>true</optional>
</dependency>
----
======

2. Run your application as usual:
+
include::ROOT:partial$app-run.adoc[]

3. That's it! The PostgreSQL container starts automatically, and your application connects to it. No configuration files, no code changes needed. The application log says where the database is:
+
[source,logs]
----
...i.a.d.s.startup  : Dev Service 'postgresql' is ready in container 9b1c4e7a2d60 (postgres, localhost:<port>)
----
+
Your `@SpringBootTest` tests use the same Dev Service, with no further setup.

[TIP]
====
Want to verify which Dev Services are running? When running the application in dev mode with Spring Boot Actuator in your classpath, check the `/actuator/devservices` endpoint (see xref:index.adoc#_actuator[Actuator]).
====

== Using Dev Services

Dev Services are available as separate modules for each supported service. You can find the complete list in the xref:_supported_services[Supported Services] section below.

Dev Services providing the same capability (e.g. JDBC databases) are mutually exclusive: if more than one is active at the same time, the application fails at startup with a clear error message pointing at the conflict.

[NOTE]
====
Dev Services are provisioned as OCI containers. Ensure you have a container runtime like https://podman-desktop.io[Podman] or https://www.docker.com[Docker] installed and running in your environment.
====

=== Service Connections

Your application is automatically configured to connect to Dev Services, which take precedence over manually configured properties. For example, when using the `arconia-dev-services-postgresql` module, the Dev Service transparently overrides properties like `spring.datasource.url`, `spring.datasource.username`, and `spring.datasource.password`.

To change how the Dev Service is configured, such as its credentials, use its own properties (for example, `arconia.dev.services.postgresql.username`), not the `spring.datasource.*` ones, which the Dev Service overrides.

The auto-configuration mechanism uses https://docs.spring.io/spring-boot/reference/testing/testcontainers.html#testing.testcontainers.service-connections[Spring Boot's Service Connections] internally to establish connections between your application and containerized services, eliminating the need for manual property configuration or test-specific setup code.

If a `ConnectionDetails` bean of the type a Dev Service provides already exists in your application (for example, a `JdbcConnectionDetails` bean you define, or one Spring Boot Docker Compose provides), the application connects to that service instead: the Dev Service is not started, and a message says so at startup.

=== Lifecycle Management

Arconia instructs Spring Boot to manage the lifecycle of Dev Services as beans in the application context:

* Startup: Services start when the application context initializes.
* Shutdown: Services stop when the application stops.
* Persistence: Services remain available throughout the lifecycle of your application or tests.

When using https://docs.spring.io/spring-boot/reference/using/devtools.html[Spring Boot DevTools] in dev mode, Dev Services are not recreated on restart. They remain running in the background until the application process exits, ensuring a smooth development experience without wait times or state loss. When the process exits, the containers it kept are stopped, unless they are kept by the `testcontainers` reuse strategy (see xref:index.adoc#_reusing_dev_services[Reusing Dev Services]). A process killed outright cannot stop them; the container runtime then removes them a few seconds later through Testcontainers' resource reaper.

Since the container is kept, changes to the configuration of a Dev Service take effect once you stop and start the application again. The same applies to disabling a Dev Service: its kept container runs until the application process exits. The only container replaced on restart is one that is no longer running, for example, because it was removed manually.

A Dev Service can also use a container that is already running instead of starting a new one, which changes when the container is stopped. See xref:index.adoc#_reusing_dev_services[Reusing Dev Services].

=== Dev Services in Test Mode

In test mode, every test application context starts its own containers and stops them when it closes, to ensure test isolation, consistency, and reliability. The features that keep or share containers are only available in dev mode: the reuse strategies, the persistence across Spring Boot DevTools restarts, and the `devservices` actuator endpoint.

Spring caches test application contexts, so the test classes sharing a context also share its containers. A test class with a different configuration gets its own context and starts its own set of containers: different properties, a different set of mocked beans (`@MockitoBean`), a test slice, or `@DirtiesContext` all lead to a new context. To keep the suite fast, put the configuration your tests share in an `application-test.yml` file or a common base class rather than on individual test classes, and consider starting containers in parallel (see xref:index.adoc#_startup_sequence[Startup Sequence]). The `spring.test.context.cache.maxSize` property limits how many contexts, and so how many sets of containers, are kept alive at once.

The observability Dev Services (xref:lgtm.adoc[Grafana LGTM], xref:otel-collector.adoc[OpenTelemetry Collector], xref:phoenix.adoc[Phoenix], xref:openlit.adoc[OpenLIT], and xref:langfuse.adoc[Langfuse]) are skipped in test mode by default, since most tests have no use for a telemetry backend. For the tests that verify the telemetry the application exports, set the `arconia.dev.services.<service-name>.skip-in-tests` property to `false`. Prefer a configuration those tests share, such as a dedicated profile, over properties on each test class, which would start a new context and new containers for each of them:

[source,yaml]
----
# application-telemetry-test.yml
arconia:
  dev:
    services:
      lgtm:
        skip-in-tests: false
----

[source,java]
----
@SpringBootTest
@ActiveProfiles("telemetry-test")
class TelemetryTests {
    ...
}
----

=== Configuration Options

Each Dev Service can be customized through Spring Boot configuration properties. All Dev Services support a common set of properties under the `arconia.dev.services.<service-name>` prefix.

==== Common Properties

The following properties are available for all Dev Services. Each Dev Service page lists its defaults.

|===
|Property |Default |Description

| `arconia.dev.services.<service-name>.enabled`
| `true`
| Whether the dev service is enabled.

| `arconia.dev.services.<service-name>.image-name`
| Varies by service
| Full name of the container image used in the dev service.

| `arconia.dev.services.<service-name>.environment`
| `{}`
| Environment variables to set in the service.

| `arconia.dev.services.<service-name>.network-aliases`
| `[]`
| Additional hostnames the dev service container is reachable by on the shared network, next to the name of the dev service. Only applicable when the shared network is enabled.

| `arconia.dev.services.<service-name>.port`
| `0`
| Fixed port for exposing the primary service port to the host. When it's 0 (default), a random available port is assigned dynamically.

| `arconia.dev.services.<service-name>.resources`
| `[]`
| Resources from the classpath or host filesystem to copy into the container. They can be files or directories that will be copied to the specified destination path inside the container at startup and are immutable (read-only).

| `arconia.dev.services.<service-name>.reuse-strategy`
| Varies by service
| Strategy for reusing a running container for the dev service across applications or restarts. Only applicable in dev mode. See xref:index.adoc#_reusing_dev_services[Reusing Dev Services].

| `arconia.dev.services.<service-name>.startup-timeout`
| `60s`, or `120s` for slow-starting services
| Maximum waiting time for the service to start, counted from the container start.

| `arconia.dev.services.<service-name>.volumes`
| `[]`
| Files or directories to mount from the host filesystem into the container. They are mounted at the specified destination path inside the container at startup and are mutable (read-write). Changes in either the host or the container will be immediately reflected in the other.
|===

==== Global Properties

To disable all Dev Services at once, set the `arconia.dev.services.enabled` property to `false`.

The `arconia.dev.services.network.enabled` property (default `false`) turns on the shared network: when enabled, all Dev Service containers join a common OCI network so they can reach each other by name (see xref:index.adoc#_shared_network[Shared Network]).

[NOTE]
====
Disabling Dev Services globally overrides individual service settings. If global disabling is set, no Dev Services will start, regardless of their individual `enabled` properties. If you want to disable only specific services, leave the global setting enabled and configure individual services instead via the `arconia.dev.services.<service-name>.enabled` property.
====

==== Service-Specific Properties

Individual services provide additional configuration properties. Refer to each service's documentation for all available configuration options.

=== Programmatic Customization

Configuration properties cover the most common scenarios. When you need full control over a container (for example, a custom wait strategy, a startup check strategy, extra labels, or additional commands), you can define a `DevServiceContainerCustomizer<T>` bean. Every customizer is applied to any Dev Service container that is an instance of its generic type `T`, right after the container is created and before it is started.

For example, to customize the wait strategy of the PostgreSQL Dev Service (using `org.testcontainers.postgresql.PostgreSQLContainer`):

[source,java]
----
@Configuration(proxyBeanMethods = false)
public class DevServicesConfiguration {

    @Bean
    DevServiceContainerCustomizer<PostgreSQLContainer> postgresCustomizer() {
        return container -> container.waitingFor(Wait.forListeningPort()
                .withStartupTimeout(Duration.ofMinutes(1)));
    }

}
----

A wait strategy set by a customizer replaces the one the Dev Service configured, including the `startup-timeout` property applied to it. Set the timeout on the new strategy, as in the example above.

A customizer typed on a common supertype (e.g. `GenericContainer<?>`) applies to all Dev Service containers. When multiple customizers match the same container, they are applied following the semantics of the `@Order` annotation and `Ordered` interface.

Customizers use classes from the Dev Service and Testcontainers dependencies, which you scope to development and tests. Define them the same way: in a dedicated module of your build that depends on the Dev Service, register the configuration class as an auto-configuration in its `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` file, and add the module to your application as a development and test only dependency, as you do for the Arconia Dev Services:

[tabs]
======
Gradle::
+
[source,groovy]
----
dependencies {
    testAndDevelopmentOnly project(':dev-services')
}
----

Maven::
+
[source,xml]
----
<dependency>
    <groupId>com.example</groupId>
    <artifactId>dev-services</artifactId>
    <scope>runtime</scope>
    <optional>true</optional>
</dependency>
----
======

The customizers then apply whenever the Dev Services do, when running the application in dev mode and in your tests, and never reach your production build.

=== Reusing Dev Services

An application can start its own container for a Dev Service and stop it on shutdown, or use a container that is already running instead of starting a new one. The `arconia.dev.services.<service-name>.reuse-strategy` property decides which. It accepts three values.

[cols="1,3,2,2"]
|===
| Value | Behavior | Container Lifetime | Setup

| `framework`
| Arconia looks for a running container that provides the same Dev Service, started by another application, and connects to it. If none is found, the application starts its own container, which other applications can discover in turn.
| Stopped when the application that started it stops.
| None.

| `testcontainers`
| The container is kept running across application runs, relying on the https://java.testcontainers.org/features/reuse/[Reusable Containers] feature of Testcontainers. The application connects to an existing container only if it was created with the same configuration.
| Never stopped automatically: you are in charge of cleaning up.
| You enable the feature on your machine.

| `none`
| A new container is always started.
| Stopped when the application stops.
| None.
|===

The default depends on the Dev Service. It is `framework` for services that several applications typically use together, such as message brokers, identity providers, observability platforms, and resource-intensive services, and `none` for the others, such as databases. Each Dev Service page lists its default.

The two reuse strategies are mutually exclusive. A container kept running by Testcontainers is never discovered through the `framework` strategy, and the other way around.

[NOTE]
====
Reuse is only applicable in dev mode (see xref:index.adoc#_dev_services_in_test_mode[Dev Services in Test Mode]).
====

==== Framework Strategy

The `framework` strategy lets multiple applications running simultaneously during development use the same containerized service instead of starting one container each. This is particularly useful for:

* Distributed systems: Share a message broker (e.g., RabbitMQ, Kafka) or observability platform (e.g. Grafana LGTM) across multiple services.
* Resource efficiency: Avoid running duplicate containers for the same service, especially for resource-intensive services (e.g., Docling, Ollama).

It works out of the box, with no additional setup required. Every Dev Service container is labeled, and the application first looks for a running container that already provides the same Dev Service. If one is found, the application connects to it instead of starting a new container. Otherwise, the application starts its own container, which other applications can discover in turn.

The application that started the container owns its lifecycle: the container is stopped when that application stops. Applications that were connected to it lose access to the service at that point. The next time they start, they look for a running container again and start their own if none is found.

A discovered container is used as it runs, with the configuration of the application that started it. Application-specific customization (environment variables, resources, image name, `DevServiceContainerCustomizer` beans) doesn't apply to containers started by other applications. The application connects with its own configured settings, so any credentials must be the same across the applications using the service. For databases, that includes the username, the password, and the database name. If an application needs its own differently-configured service instance, set `arconia.dev.services.<service-name>.reuse-strategy=none` for that service.

When using Spring Boot DevTools, an application that started a container keeps using it across restarts, even if another application has started a container for the same Dev Service in the meantime.

The `framework` strategy is supported by all the Dev Services, whether or not it is their default. When it cannot be applied (see the xref:ollama.adoc[Ollama Dev Service] for the one such case), the startup message says so.

==== Testcontainers Strategy

The `testcontainers` strategy keeps a Dev Service container running across application runs. It relies on the https://java.testcontainers.org/features/reuse/[Reusable Containers] feature of Testcontainers, which is disabled by default: with this strategy, you explicitly opt into the feature and take charge of the containers it keeps. To enable it, create or edit the file `~/.testcontainers.properties` in your home directory and add the following line:

[source,properties]
----
testcontainers.reuse.enable=true
----

Alternatively, set the `TESTCONTAINERS_REUSE_ENABLE` environment variable to `true`, which is convenient on CI machines.

Once enabled, Dev Services using this strategy persist across application runs. When the feature is not enabled, the container is started and stopped with the application as usual, and the startup message says so.

Testcontainers identifies a reusable container by its configuration. Changing the configuration of the Dev Service (for example, its image, environment variables, or credentials) results in a new container being started, while the previous one keeps running. Arconia never stops a container kept by this strategy.

[WARNING]
====
Reusable containers are never removed automatically. You are in charge of stopping and removing them with your container runtime (Docker/Podman) when they are no longer required (see xref:index.adoc#_finding_and_cleaning_up_containers[Finding and Cleaning Up Containers] in Troubleshooting).
====

=== Resource Mappings

Dev Services support copying files and directories from your classpath or host filesystem into the container at startup. This can be useful for various scenarios, including for loading configuration files, seeding initialization data, or making static resources available to containerized services.

Resources are copied to the specified destination path inside the container at startup and are never changed on the host after being copied (read-only). This means that any modifications made by the container to these files will not persist or affect the source files on the host.

This strategy is preferred over mounting host directories as volumes, as it avoids potential issues with file permission mismatches, path resolution, and cross-platform compatibility.

==== Configuration

Resource mappings are configured through the `arconia.dev.services.<service-name>.resources` property. Each mapping requires two values:

* Source path: Location of the resource on the classpath or filesystem;
* Container path: Destination path inside the container.

For example, to copy a configuration file from the classpath into an OpenTelemetry Collector container:

[source,yaml]
----
arconia:
  dev:
    services:
      otel-collector:
        resources:
          - source-path: otel-collector-config.yml
            container-path: /etc/otelcol-contrib/config.yaml
----

==== Source Path Resolution

The source path supports multiple resolution strategies:

* Automatic resolution: Without a prefix, Arconia first attempts to locate the resource on the classpath. If not found, it searches the filesystem. For example, `config/database.conf` will be resolved from the classpath if available, otherwise from the filesystem.

* Explicit classpath: Use the `classpath:` prefix to load resources from the classpath. For example, `classpath:config/database.conf`.

* Explicit filesystem: Use the `file:` prefix to load resources from the host filesystem. For example, `file:./config/database.conf`.

[TIP]
Using explicit prefixes (`classpath:` or `file:`) improves clarity and readability, making it clear where the resource is being loaded from. It also avoids ambiguity and potential resolution issues, especially in complex projects with multiple resource locations.

=== Volume Mappings

Dev Services support binding files and directories from the host filesystem into the container at startup. This can be useful for various scenarios, including for persisting data generated by the containerized service or for sharing files between your host and the container.

Files or directories specified in the volume mappings are mounted from the host filesystem into the container at the specified destination path inside the container at startup and are mutable (read-write). Changes in either the host or the container will be immediately reflected in the other.

Since this provides direct read-write access between the host and container, use this feature with caution. Ensure that the mounted paths are secure and do not expose sensitive data or system files. Furthermore, be aware of potential file permission issues that may arise due to differences between the host and container environments. 

[NOTE]
====
It's recommended to use volume mappings only when necessary. Instead, consider using resource mappings for most use cases where read-only access is sufficient.
====

==== Configuration

Volume mappings are configured through the `arconia.dev.services.<service-name>.volumes` property. Each mapping requires two values:

* Host path: Location of the file or directory on the host filesystem;
* Container path: Destination path inside the container.

For example, to keep the models the Ollama Dev Service downloads in a directory of your home folder, across application runs and tests:

[source,yaml]
----
arconia:
  dev:
    services:
      ollama:
        volumes:
          - host-path: ${user.home}/.ollama
            container-path: /root/.ollama
----

=== Networks and Ports

By default, Dev Service containers are connected to the default network of your container runtime (Docker/Podman) and are accessible from your application via the local host and dynamically assigned ports.

==== Fixed Ports

By default, Dev Services use random available ports to avoid conflicts. However, you can configure fixed exposed ports when needed. Each service supports the `arconia.dev.services.<service-name>.port` property to specify a fixed port for exposing the primary service provided by the container.

Some Dev Services may expose multiple ports (e.g., management console ports). In such cases, the Dev Service will offer additional properties to configure fixed ports for those secondary services. For example, the RabbitMQ Dev Service provides the common `arconia.dev.services.rabbitmq.port` property for the main AMQP port and an additional `arconia.dev.services.rabbitmq.management-console-port` property for the management UI port.

A common use case for fixed ports is when other tools or services in your development environment need to connect to the Dev Service container using a known port, or for exposing UI consoles through well-known ports. For example, `arconia.dev.services.lgtm.port=3000` exposes Grafana on port 3000.

[WARNING]
====
Using fixed ports may cause conflicts if another service is already using the port. Consider using fixed ports only when necessary, and set them in a configuration that only applies in dev mode, such as an `application-dev.yml` file: in tests, every cached application context starts its own container, and a second container can't bind the same port.
====

=== Shared Network

This is an advanced, opt-in feature. Most applications never need it: your application always reaches Dev Services over the local host and mapped ports, with no configuration.

Dev Service containers cannot, by default, reach each other by name. When you need container-to-container communication, for example, letting a Docling Dev Service send telemetry to a Grafana LGTM Dev Service, enable the shared network globally with the `arconia.dev.services.network.enabled` property (disabled by default). When enabled, all Dev Service containers join a common OCI network and are reachable by their service name, so you only need to point the consumer at the target's service name and internal port:

[source,yaml]
----
arconia:
  dev:
    services:
      network:
        enabled: true # <1>
      docling:
        environment:
          OTEL_EXPORTER_OTLP_ENDPOINT: http://lgtm:4317 # <2>
          DOCLING_SERVE_OTEL_ENABLE_TRACES: "true"
          DOCLING_SERVE_OTEL_ENABLE_OTLP_METRICS: "true"
----
<1> A single global switch attaches every Dev Service container to the shared network.
<2> The `lgtm` hostname is the target's service name, which every container on the shared network is reachable by, and `4317` is the container's internal OTLP/gRPC port, not the host-mapped port. To reach a container by other hostnames as well, set its `network-aliases` property.

==== Advanced Scenarios

* Container reuse. The shared network doesn't combine with the `testcontainers` reuse strategy: the network is created anew with every run, and since the Testcontainers reuse hash includes it, a container kept by that strategy would never be matched again and would be left running after every run. When the shared network is enabled, the strategy is therefore not applied, and the startup message of the Dev Service says so. Use one or the other.

* Your own containers. The network is exposed as an injectable Testcontainers `Network` bean. To let a container you manage yourself reach Dev Services, enable the shared network, inject the bean, and attach your container:

[source,java]
----
@Bean
GenericContainer<?> daprContainer(Network devServicesNetwork) {
    return new GenericContainer<>("daprio/daprd:latest")
            .withNetwork(devServicesNetwork)
            .withNetworkAliases("dapr");
}
----

A user-defined `Network` bean takes precedence over the one Arconia provides.

=== SSL with Dev Services

Some Dev Services can serve SSL, so that the SSL support of your application is developed and tested against them, the way https://docs.spring.io/spring-boot/reference/testing/testcontainers.html#testing.testcontainers.service-connections.ssl[SSL with Service Connections] allows with plain Spring Boot and Testcontainers. This covers two situations:

* The application connects to the real service over SSL, in production, and you want dev and test to exercise the same path. For example, an application whose Redis is only reachable over SSL in production connects to the Redis Dev Service over SSL as well, so that its SSL client setup is covered by its tests.
* The service only accepts SSL connections, as Elasticsearch does in its default configuration, so the application has no other way to reach it.

The support builds on Spring Boot's and goes one step further: Spring Boot configures the application side, and Arconia configures the container as well. The connection uses SSL in one direction: the Dev Service presents a certificate, and the application verifies it. The application presents no certificate of its own, and the Dev Service doesn't ask for one.

SSL is configured through the `ssl` properties of the Dev Service, which describe its SSL bundle with the keys of a https://docs.spring.io/spring-boot/reference/features/ssl.html[Spring Boot SSL bundle], in PEM form (`ssl.pem`) or as a Java keystore (`ssl.jks`). The bundle has the meaning of the bundle a Spring Boot server is configured with: its key store holds the certificate and private key the Dev Service presents. There is nothing to configure on the application side: the application trusts the certificate chain the Dev Service presents through the Spring Boot service connection of the Dev Service. The `protocol` and `options` of the bundle apply to that application side, as for any Spring Boot SSL bundle: they configure the client the application connects with, not the Dev Service container.

[source,yaml]
----
arconia:
  dev:
    services:
      redis:
        ssl:
          enabled: true
          pem:
            keystore:
              certificate: "classpath:certs/redis.crt"
              private-key: "classpath:certs/redis.key"
----

Certificates and keys are read as for any Spring Boot SSL bundle: from a `classpath:` or `file:` location, as inline PEM content, or as `base64:` content. Whatever form they are configured in, each Dev Service gets them in the form its service expects. The `ssl.pem` and `ssl.jks` properties take the `keystore`, `key`, `options`, and `protocol` keys of a `spring.ssl.bundle` definition, with the same names and meaning. A trust store is not part of them, since the Dev Service never asks the application for a certificate. When `ssl.enabled` is `false`, the other `ssl` properties have no effect.

==== Certificate Requirements

The clients verify the host name of the Dev Service against its certificate, so the certificate must be valid for the host the application connects to: `localhost` and `127.0.0.1` with a local container runtime, the host of the container runtime otherwise, and the name of the Dev Service and its `network-aliases` when the application reaches it over the xref:index.adoc#_shared_network[shared network]. A certificate for local development can be generated with OpenSSL, for example:

[source,shell]
----
openssl req -x509 -newkey rsa:2048 -nodes -days 365 \
  -keyout redis.key -out redis.crt -subj "/CN=localhost" \
  -addext "subjectAltName=DNS:localhost,IP:127.0.0.1,IP:::1,DNS:redis"
----

The private key must be readable by Arconia, which copies it into the container unencrypted, where the service reads it. Certificates and keys for development are not secrets, but keep them out of the resources packaged for production anyway.

The bundle the application connects to the Dev Service with, which trusts the certificate the Dev Service presents, is registered in the `SslBundles` of the application under the name `dev-services-<service-name>`, so Spring Boot tooling reports it as any other bundle: the SSL information of the `info` actuator endpoint, when enabled, lists the trusted certificate chain, and the `devservices` endpoint reports it for the Dev Service (see xref:index.adoc#_actuator[Actuator]). The `dev-services-` prefix is reserved for these bundles. The startup message of the Dev Service says SSL is enabled (see xref:index.adoc#_startup_feedback[Startup Feedback]).

The container is configured for SSL right after the common properties are applied and before your xref:index.adoc#_programmatic_customization[`DevServiceContainerCustomizer`] beans run, so a customizer replacing the command or the configuration of the container must preserve the SSL part. A container kept across a Spring Boot DevTools restart keeps the SSL configuration it was started with, like the rest of its configuration: stop and start the application after changing the `ssl` properties (see xref:index.adoc#_lifecycle_management[Lifecycle Management]).

The following Dev Services support SSL: xref:elasticsearch.adoc[Elasticsearch], xref:kafka.adoc[Kafka], xref:mongodb.adoc[MongoDB], xref:rabbitmq.adoc[RabbitMQ], and xref:redis.adoc[Redis]. The Elasticsearch Dev Service also works with the certificate Elasticsearch generates itself, with no certificate configured at all.

[NOTE]
====
When an application connects to a Dev Service started by another application (see xref:index.adoc#_reusing_dev_services[Reusing Dev Services]), it uses the bundle built from its own `ssl` properties. All the applications sharing the Dev Service must configure the same `ssl` properties, as they must use the same credentials. A mismatch, such as SSL enabled in one application only or different certificates, shows up as a connection or handshake failure when the application first uses the service.
====

=== Startup Sequence

Control how Dev Services start using the `spring.testcontainers.beans.startup` property of Spring Boot. It can be set to `parallel` or `sequential`. By default, containers are started sequentially, so the startup time is the sum of the startup times of all the containers. With `parallel`, it is the startup time of the slowest one, which pays off as soon as an application uses two or more Dev Services that take a while to start, such as Keycloak and Elasticsearch, and also when images are pulled for the first time. The property applies to every Testcontainers container of the application, not only Dev Services. Set it in `application.yml`, so that your tests benefit from it too:

[source,yaml]
----
spring:
  testcontainers:
    beans:
      startup: parallel
----

=== Startup Feedback

When a Dev Service is ready, Arconia logs a consistent startup message: one line about the container the Dev Service runs in, and one line with its links, such as management consoles and telemetry endpoints, when it has any:

[source,logs]
----
...i.a.d.s.startup  : Dev Service 'lgtm' is ready in container 3f2a9c1d7b4e (grafana/otel-lgtm, localhost:<port>, reuse-strategy: framework)
...i.a.d.s.startup  : Dev Service 'lgtm' links: Grafana: http://localhost:32895, OTLP/HTTP: http://localhost:32896, OTLP/gRPC: http://localhost:32897, Prometheus: http://localhost:32898, Tempo MCP: http://localhost:32899/api/mcp
----

The first line states:

* the container image;
* the address of the main port of the service on the host, which is what you need to connect a tool on your machine to it;
* `started by another application` or `kept across restart`, when applicable (see xref:index.adoc#_reusing_dev_services[Reusing Dev Services]);
* the reuse strategy in effect, when a container is reused;
* `ssl`, when SSL is enabled for the Dev Service.

When the configured reuse strategy could not be applied, the line says so and gives the reason in parentheses, for example, because the Testcontainers reusable containers feature is not enabled on your machine:

[source,logs]
----
...i.a.d.s.startup  : Dev Service 'lgtm' is ready in container 3f2a9c1d7b4e (grafana/otel-lgtm, localhost:<port>, started by another application, reuse-strategy: framework)
...i.a.d.s.startup  : Dev Service 'postgresql' is ready in container 9b1c4e7a2d60 (postgres, localhost:<port>, kept across restart)
...i.a.d.s.startup  : Dev Service 'redis' is ready in container 5e8d2b7f0c13 (redis, localhost:<port>, reuse-strategy: none ('testcontainers' requires reuse to be enabled in the Testcontainers configuration (testcontainers.reuse.enable=true in ~/.testcontainers.properties or TESTCONTAINERS_REUSE_ENABLE=true)), ssl)
----

The links are declared by each Dev Service and resolved against the container it runs in, whether the application started it or discovered it. The same information is available programmatically through the `devservices` actuator endpoint (see xref:index.adoc#_actuator[Actuator]), for each service under a `links` list of `label` and `url`, together with all the host ports the container publishes.

The messages are written by the `io.arconia.dev.services.startup` logger. To keep only them, quiet the logging of Testcontainers (see xref:index.adoc#_troubleshooting[Troubleshooting]).

=== Ahead-of-Time Processing and Native Images

Dev Services are a dev and test time feature. Spring AOT processing of an application and native images imply the prod mode, in which Dev Services are not active at all.

In AOT-processed tests (`spring.aot.enabled=true`), Dev Services are excluded from the generated code and are not available: their beans are created at startup from the state of the container runtime, which cannot be decided ahead of time. This is the same limitation Spring Boot has for `@ServiceConnection` on `@Bean` methods, `@ImportTestcontainers`, and Docker Compose in AOT-processed tests. Run tests that rely on Dev Services without AOT.

== Actuator

When running the application in dev mode, a `devservices` actuator endpoint is auto-configured if https://docs.spring.io/spring-boot/reference/actuator/enabling.html[Spring Boot Actuator] is present in the classpath. This endpoint exposes information about the running Dev Services containers, helping you inspect and debug your development environment.

By default, Spring Boot exposes only the `health` endpoint over HTTP. To access the `devservices` endpoint, include it in the https://docs.spring.io/spring-boot/reference/actuator/endpoints.html#actuator.endpoints.exposing[web exposure configuration]:

[source,yaml]
----
management:
  endpoints:
    web:
      exposure:
        include: devservices
----

== Troubleshooting

=== When a Container Fails to Start

When a container fails to start, Testcontainers writes the container's logs to the application log at error level, followed by the exception that stops the application. The common causes are:

* The container runtime is not running or not reachable: Spring Boot reports that no valid Docker environment was found. Start Docker or Podman, and make sure Testcontainers can reach it.
* A fixed port is already in use: the container runtime refuses to publish the port. Free the port, or remove the `port` property of the Dev Service (or the additional port property involved) to use a random port.
* The service exits during startup: the container logs written above the exception say why, such as an invalid configuration passed through the `environment` property.

Spring Boot starts all the containers of the application together, so the exception may name the bean of another Dev Service than the one that failed. The image named in the cause of the exception identifies the container that failed.

=== Running Without a Container Runtime

To run the application or the tests without a container runtime, disable the Dev Services with `arconia.dev.services.enabled=false` and configure the connections yourself, for example with `spring.datasource.url`.

=== Showing the Logs of a Container

Dev Services don't forward the logs of their containers to the application log, except when a container fails to start. To follow the logs of a container while the application runs, attach a log consumer to it with a `DevServiceContainerCustomizer` (see xref:index.adoc#_programmatic_customization[Programmatic Customization]):

[source,java]
----
@Configuration(proxyBeanMethods = false)
class ContainerLogsConfiguration {

    @Bean
    DevServiceContainerCustomizer<GenericContainer<?>> containerLogs() {
        return container -> container.withLogConsumer(
                new Slf4jLogConsumer(LoggerFactory.getLogger("dev-services")).withPrefix(container.getDockerImageName()));
    }

}
----

Declare the bean in the module holding your Dev Service customizations (see xref:index.adoc#_programmatic_customization[Programmatic Customization]). The logs are written at info level under the `dev-services` logger, each line prefixed with the image of the container.

=== Quieting the Testcontainers Logs

Testcontainers logs its own progress (connecting to the container runtime, pulling images, starting containers) at info level, next to the startup message of each Dev Service. To keep only the Arconia messages, set `logging.level.org.testcontainers=WARN` and `logging.level.tc=WARN`.

=== Podman Closing Idle Connections

With Podman, a container sometimes fails to start with `NoHttpResponseException: localhost:2375 failed to respond` or `Broken pipe`. The Podman API service drops idle connections after a few seconds, as set by its `service_timeout` option (5 seconds by default), and Testcontainers can send a request over a connection Podman has just closed (see https://github.com/testcontainers/testcontainers-java/issues/7310[testcontainers-java#7310]). Disable the timeout, for example on a Podman machine:

[source,shell]
----
podman machine ssh -- 'sudo mkdir -p /etc/containers/containers.conf.d && printf "[engine]\nservice_timeout = 0\n" | sudo tee /etc/containers/containers.conf.d/service-timeout.conf'
podman machine stop && podman machine start
----

On Linux without a Podman machine, set `service_timeout = 0` in the `[engine]` section of `~/.config/containers/containers.conf`, then restart the API service with `systemctl --user restart podman.socket`.

=== Finding and Cleaning Up Containers

The startup message of each Dev Service reports the container it runs in, and the reuse strategy in effect (see xref:index.adoc#_startup_feedback[Startup Feedback]). Every Dev Service container also carries the `io.arconia.dev-service.name` label, holding the name of the Dev Service, so you can list the containers with your container runtime:

[source,shell]
----
docker ps --filter label=io.arconia.dev-service.name
docker ps --filter label=io.arconia.dev-service.name=rabbitmq
----

To stop and remove all the Dev Service containers left running, including the ones kept by the `testcontainers` strategy:

[source,shell]
----
docker rm -f $(docker ps -q --filter label=io.arconia.dev-service.name)
----

== Arconia Dev Services vs. Spring Boot Development-time Services

Arconia Dev Services is a higher-level abstraction built on top of Spring Boot's Testcontainers support. While both approaches leverage Testcontainers for provisioning services, Arconia Dev Services provides a more streamlined, zero-configuration experience.

=== Key Differences

The primary distinction is simplicity. Arconia Dev Services eliminates boilerplate code and configuration, allowing you to focus on development rather than infrastructure setup.

[tabs]
======
Arconia Dev Services::
+
[source,groovy]
----
dependencies {
    testAndDevelopmentOnly 'io.arconia:arconia-dev-services-postgresql'
}
----
+
Run your application normally:
+
[source,shell]
----
./gradlew bootRun
----

Spring Boot Development-time Services::
+
[source,groovy]
----
dependencies {
    testAndDevelopmentOnly 'org.springframework.boot:spring-boot-testcontainers'
    testAndDevelopmentOnly 'org.testcontainers:postgresql'
}
----
+
Create a test configuration class:
+
[source,java]
----
@TestConfiguration(proxyBeanMethods = false)
public class TestContainersConfiguration {

    @Bean
    @ServiceConnection
    @RestartScope
    PostgreSQLContainer postgresContainer() {
        return new PostgreSQLContainer("postgres:latest");
    }
}
----
+
Create a test main class:
+
[source,java]
----
public class TestApplication {

    public static void main(String[] args) {
        SpringApplication.from(Application::main)
            .with(TestContainersConfiguration.class)
            .run(args);
    }
}
----
+
Run from the test classpath:
+
[source,shell]
----
./gradlew bootTestRun
----
+
Import the Testcontainers configuration in each test class needing the service:
+
[source,java]
----
@SpringBootTest
@Import(TestContainersConfiguration.class)
class ApplicationTests {
}
----
======

=== Migration Path

If your project already uses Spring Boot's Testcontainers support, you can adopt Arconia Dev Services incrementally:

1. Add Arconia dependencies for services you want to manage automatically.
2. Keep existing Testcontainers configuration for custom or unsupported services.
3. Gradually migrate more services to Arconia as needed.

Both approaches work alongside each other, allowing smooth transitions without disrupting your workflow.

[NOTE]
====
Coexistence is per service. When your application defines its own `ConnectionDetails` bean for a service, the corresponding Arconia Dev Service is not started (see xref:index.adoc#_service_connections[Service Connections]). A `@ServiceConnection` container declared as a `@Bean`, as in the example above, doesn't count as such a bean: while you keep it, disable the corresponding Arconia Dev Service with its `enabled` property. Once you adopt the Arconia Dev Service for a given service, remove your own container definition for that same service.
====

=== Spring Boot Docker Compose

Arconia Dev Services and https://docs.spring.io/spring-boot/reference/features/dev-services.html#features.dev-services.docker-compose[Spring Boot Docker Compose] can be used in the same application. Spring Boot starts the services of the Compose file and provides their `ConnectionDetails` before the Dev Services are registered, so a Dev Service for a service that the Compose file also provides is not started (see xref:index.adoc#_service_connections[Service Connections]), while the Dev Services for the other services start as usual. In tests, Spring Boot skips Docker Compose by default, so the Dev Services provide every service. To settle on one of the two for a given service, disable the Dev Service with its `enabled` property, or disable Spring Boot Docker Compose with `spring.docker.compose.enabled=false`.
