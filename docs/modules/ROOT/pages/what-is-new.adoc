[[what-is-new]]
= What's New in Arconia {page-component-version}

Arconia {page-component-version} provides a number of new features and enhancements. This page includes the highlights of the release, but you can also check out the full https://github.com/arconia-io/arconia/releases[release notes] for more details about each new feature and bug fix.

We provide an automated way to upgrade your project to the latest version of Arconia, which is described in the xref:upgrading-arconia.adoc[Upgrading Arconia] documentation.

== Dev Services

* Test slices now pick up the Dev Service of their technology with no further configuration: `@JdbcTest`, `@DataJdbcTest`, `@DataJpaTest`, and `@JooqTest` for the JDBC Dev Services, `@DataMongoTest`, `@DataRedisTest`, `@DataElasticsearchTest`, and `@DataLdapTest`. For the JDBC slices, the Dev Service replaces the embedded database Spring Boot would otherwise configure; disable the Dev Service for a test with its `enabled` property to get the embedded database back. Learn more on the page of each Dev Service, for example the xref:dev-services:postgresql.adoc#_running_the_application[PostgreSQL Dev Service].
* The observability Dev Services (Grafana LGTM, OpenTelemetry Collector, Phoenix, and OpenLit) are now skipped in test mode by default, since most tests have no use for a telemetry backend. Set `arconia.dev.services.<service-name>.skip-in-tests` to `false` for the tests that verify the telemetry the application exports. Learn more about xref:dev-services:index.adoc#_dev_services_in_test_mode[Dev Services in Test Mode].
* When the application process exits, the containers it kept across Spring Boot DevTools restarts are now stopped, instead of being left to the Testcontainers resource reaper a few seconds later. Another application can no longer connect to a container that is about to disappear. Containers kept by the `testcontainers` reuse strategy are still left running. Learn more about xref:dev-services:index.adoc#_lifecycle_management[Lifecycle Management].
* The startup message of a Dev Service now includes the host address of its main port, which is what you need to connect a tool on your machine to it, and only mentions the reuse strategy when a container is reused or the configured strategy could not be applied. Learn more about xref:dev-services:index.adoc#_startup_feedback[Startup Feedback].
* The default `startup-timeout` of the Dev Services is now 60 seconds, as in Testcontainers, instead of 30 seconds. The Dev Services that take longer to start keep their 120 seconds default.
* An application connecting to a Dev Service started by another application now honors the configuration set through the `environment` property of the Dev Service, as the application that started it does: the region of Floci, the base DN and password of LLDAP, and the API key of Docling.
* Two Dev Services of the same category, such as two JDBC databases, now fail at startup also when one of them connects to a container started by another application, instead of the second one being silently skipped.
* A new xref:dev-services:index.adoc#_troubleshooting[Troubleshooting] section covers containers that fail to start, running without a container runtime, showing the logs of a container in the application log, and Podman closing idle connections. The documentation also explains how Dev Services work together with xref:dev-services:index.adoc#_spring_boot_docker_compose[Spring Boot Docker Compose], how test application contexts share containers, and how to start containers in parallel.

=== Building Dev Services

The following changes affect the custom Dev Services you build on the Arconia Dev Services API. The xref:upgrading-arconia.adoc[upgrade recipe] applies the renames.

* `BaseDevServicesProperties` has been renamed to `DevServicesProperties`.
* `DevServiceRegistration` and `ContainerInfo` are classes with getters instead of records, so that they can describe more about a Dev Service in the future without breaking changes: `registration.name()` becomes `registration.getName()`, `containerInfo.imageName()` becomes `containerInfo.getImageName()`, and so on. Create instances with their builders. `DevServiceRegistration` also reports the category of the Dev Service, which the `devservices` actuator endpoint now includes.
* `DevServiceSslConfigurer` accepts any Testcontainers `Container`, like `DevServiceContainerCustomizer`.
* `DiscoveredContainer` is a class instead of a record, so that it can carry more information in the future without breaking changes. Its accessors and builder are unchanged.
* The methods of `DevServicesRegistrar` called by Spring are now `final`. Implement `registerDevServices` only.
* A Dev Service auto-configuration only needs to be ordered before Spring Boot's `ServiceConnectionAutoConfiguration`: ordering it after `DevServicesAutoConfiguration` is no longer necessary. Learn more about xref:dev-services:custom-dev-services.adoc[Building Your Own Dev Service].

=== Docling

* The Docling Dev Service now uses the `ghcr.io/docling-project/docling-serve-cpu` image by default, less than half the size of the image with GPU support, which the Dev Service never used.
* The `arconia.dev.services.docling.enable-ui` property has been renamed to `arconia.dev.services.docling.ui-enabled`, consistent with the other boolean properties. The xref:upgrading-arconia.adoc[upgrade recipe] renames it.

=== Elasticsearch

* An application connecting to an Elasticsearch Dev Service started by another application now uses the password configured through the `ELASTIC_PASSWORD` environment variable, as the application that started it does.
* The Elasticsearch Dev Service now runs with a heap of 512 MB to 1 GB (`ES_JAVA_OPTS=-Xms512m -Xmx1g`), instead of the fixed 2 GB Testcontainers configures. Override it through the `environment` property.

=== LLDAP

* The LLDAP Dev Service now starts with its default configuration, with the `admin` user and the `password` password. Learn more about the xref:dev-services:lldap.adoc[LLDAP Dev Service].

=== MongoDB

* The MongoDB Dev Service runs a single-node replica set again, so that transactions and change streams work as they do in production.
* The MongoDB Dev Service now starts on Linux kernels 6.19 to 7.0, which MongoDB 8.0 and later refuse to run on with their default memory allocator settings (https://jira.mongodb.org/browse/SERVER-121912[SERVER-121912]).

=== Ollama

* The OpenAI compatibility of the Ollama Dev Service now works with Spring AI 2: the `spring.ai.openai.base-url` property points to the OpenAI-compatible API of Ollama, under `/v1`, where requests previously failed with a 404 error.

=== Keycloak

* The Keycloak Dev Service now imports several realm files, each holding a single realm or a list of realms in the formats Keycloak exports, so that an application with a realm per tenant can run against all of them. The files are configured in `arconia.dev.services.keycloak.realm.import-paths` (replacing the previous `arconia.dev.services.keycloak.realm.import-path` property), and `arconia.dev.services.keycloak.realm.name` selects the realm the application connects to. Learn more about xref:dev-services:keycloak.adoc#_importing_realms[Importing Realms].

== Multitenancy

* Tenant resolution is now a chain. The `arconia.multitenancy.resolution.http.resolution-mode` property accepts a list of modes, consulted in order until one resolves a tenant, so that `subdomain, header` reads the tenant from the subdomain when the host matches and from the header otherwise. A custom `HttpRequestTenantResolver` bean still replaces the configured chain, and the new `CompositeHttpRequestTenantResolver` lets it combine custom and built-in resolvers. A resolver may now throw an `InvalidTenantIdentifierException` for input that is present but unusable, which stops the chain. Learn more about xref:multitenancy:web.adoc#_http_tenant_resolution[HTTP Tenant Resolution] and the xref:multitenancy:architecture.adoc[Architecture].
* Tenants can be resolved from the request path with the new `path` mode and a pattern such as `/tenants/{tenant}/**`, and from the subdomain with the `subdomain` mode and a pattern for the request host such as `{tenant}.example.com`. Both patterns follow the syntax of Spring MVC request mappings. Learn more about xref:multitenancy:web.adoc#_path_based_resolution[Path-Based Resolution] and xref:multitenancy:web.adoc#_subdomain_based_resolution[Subdomain-Based Resolution].
* The fixed tenant is now a resolution mode. `arconia.multitenancy.resolution.http.resolution-mode=fixed` turns the application into a single-tenant deployment, and `header, fixed` makes the fixed tenant the default tenant for requests without one. The `arconia.multitenancy.resolution.fixed.enabled` property has been removed accordingly. Learn more about xref:multitenancy:web.adoc#_fixed_tenant_and_default_tenant[Fixed Tenant and Default Tenant].
* The tenant identifier policy is configurable with `arconia.multitenancy.identifier.max-length` and `arconia.multitenancy.identifier.pattern`. Learn more about xref:multitenancy:tenant-details.adoc#_tenant_identifier_validation[Tenant Identifier Validation].
* Requests without a usable tenant are handed to a `TenantResolutionFailureHandler`, so that an application can redirect to a tenant selection page or apply its own error conventions instead of the default `application/problem+json` response. Rejections are now logged at `DEBUG` level, and a request carrying the tenant header or cookie more than once is rejected. Learn more about xref:multitenancy:web.adoc#_failure_responses[Failure Responses].
* The core and web modules have a new package layout, with `resolution`, `context` and `tenantdetails` packages replacing the previous `context.resolvers`, `context.events`, `exceptions`, `context.filters` and `context.annotations` packages, and `PropertiesTenantDetailsService` has become `InMemoryTenantDetailsService`. The xref:upgrading-arconia.adoc[upgrade recipe] rewrites imports and the removed property.
* The tenant details health indicator has been removed. Spring Boot's `db` health indicator already reports whether the database holding the tenant details can be reached, and a missing tenant details table makes the tenant filter answer with `503 Service Unavailable` and log the cause. The `management.health.tenantdetails.enabled` property no longer has any effect.

== Observability

* Content capturing in the Generative AI conventions is now configured by three switches that every flavor honors: `arconia.observations.conventions.opentelemetry.ai.capture-message-content`, `capture-tool-definitions`, and `capture-tool-call-content`. They replace the `capture-content`, `include-tool-definitions`, and `include-tool-call-content` properties. Previously, some values of `capture-content` were silently ignored by some flavors, turning content capturing off: the `openllmetry` and `openlit` flavors captured content only with `span-attributes`, and the `langsmith` flavor always recorded span events. Each of these flavors now records the content where its platform expects it. The xref:upgrading-arconia.adoc[upgrade recipe] migrates the properties.
* With the `opentelemetry` flavor, the new `arconia.observations.conventions.opentelemetry.ai.inference-content-destination` property decides where the captured messages and tool definitions of a model call are recorded: as span attributes (default), in a span event, or in a `gen_ai.client.inference.operation.details` event exported through the OpenTelemetry Logs API, with the content in structured form and correlated with the span of the model call. Tool definitions now follow the messages, instead of always being recorded as span attributes. Learn more about xref:observability:semantic-conventions/opentelemetry.adoc#_content_capturing[Content Capturing].
* The duration of chat, embedding, and image model calls is now reported with the `gen_ai.client.operation.duration` metric defined by the OpenTelemetry Semantic Conventions, instead of `gen_ai.client.operation`, for all the flavors of the Generative AI conventions. Dashboards and alerts using the previous name (for example, `gen_ai_client_operation_seconds` in Prometheus) should be updated.
* Spring AI `ChatClient` calls are now reported as agent invocations, following the OpenTelemetry Semantic Conventions: the span is named `invoke_agent` and has `gen_ai.operation.name` set to `invoke_agent` instead of `invoke_workflow`, which the conventions reserve for processes coordinating several agents. The span also records the requested model as `gen_ai.request.model` when the prompt options set it, while the streaming flag moves back to Spring AI's `spring.ai.chat.client.stream` attribute, since the conventions don't define `gen_ai.request.stream` for agent invocations. The `OpenTelemetryChatClientEventObservationHandler` has been removed: the input and output messages of a chat client call are recorded on its span only with the `span-attributes` content destination. Learn more about xref:observability:semantic-conventions/opentelemetry.adoc#_content_capturing[Content Capturing].
* The OpenTelemetry Semantic Conventions now record the stable `error.type` attribute on every observation ending in an error, with the canonical class name of the error (for example, `com.example.OrderService.OrderNotFoundException` for a nested class), on both spans and metrics, including the Generative AI ones. It's not recorded for successful operations, so the `none` value Spring Framework sets on successful HTTP server requests is removed, while HTTP server requests answered with a `5xx` status now get the status code, also when an exception was thrown, consistent with the HTTP client conventions and the OpenTelemetry Java instrumentation. Disable it with `arconia.observations.conventions.opentelemetry.error.enabled=false`. Learn more about xref:observability:semantic-conventions/opentelemetry.adoc#_errors[Errors].
* The OpenTelemetry JVM conventions no longer publish the Micrometer `jvm.threads.live` metric, which duplicated the `jvm.thread.count` metric defined by the OpenTelemetry Semantic Conventions: use `sum(jvm_thread_count_threads)` in Prometheus instead of `jvm_threads_live`. The JVM dashboard of the Grafana LGTM Dev Service has been updated accordingly.
* The `jvm.gc.duration` metric is now exported as a single metric with the description defined by the OpenTelemetry Semantic Conventions. Previously, the Micrometer OTLP registry exported it as two metrics with the same name, one for garbage collection pauses and one for concurrent phases, since they had different descriptions.
* The OpenTelemetry HTTP server conventions now record `http.request.method_original` only when the request method is not a known one and is reported as `_OTHER`, as the conventions require, instead of on every request. `CONNECT` requests are now reported with their method instead of `_OTHER`.
* The OpenTelemetry HTTP server conventions now record `http.route`, `http.response.status_code`, `url.scheme`, `url.path`, and `network.protocol.version` only when their value is available, as the conventions require, instead of placeholder values such as `UNKNOWN`, `NOT_FOUND`, or `REDIRECTION` for `http.route`. The root route is recorded as `/` instead of `root`, and the span of a request matching it is named after it, as in `GET /`. No information is lost: requests that match no route are now identified by the missing `http.route` together with `http.response.status_code`, so dashboards and alerts filtering on `http.route` values such as `NOT_FOUND` or `REDIRECTION` should filter on a missing `http.route` and the status code instead (for example, `http_route="", http_response_status_code="404"` in PromQL).
* The `arconia.observations.conventions.opentelemetry.http.include-url-query` property has been renamed to `arconia.observations.conventions.opentelemetry.http.capture-url-query`, consistent with the other properties enabling the capture of potentially sensitive data. The xref:upgrading-arconia.adoc[upgrade recipe] renames it.
* The OpenTelemetry HTTP server observations now capture the URL query string as `url.query` by default, since the OpenTelemetry Semantic Conventions require it when the request has one. The values of sensitive query parameters, such as the signatures and credentials of pre-signed cloud storage URLs, are now replaced by `REDACTED`, as the OpenTelemetry Semantic Conventions recommend. The list of parameters is configurable through `arconia.observations.conventions.opentelemetry.http.sensitive-query-parameters`, and the capture can be disabled with `arconia.observations.conventions.opentelemetry.http.capture-url-query=false`. Learn more about the xref:observability:semantic-conventions/opentelemetry.adoc#_http[HTTP] conventions.
* The OpenTelemetry Semantic Conventions now cover HTTP client requests made with the `RestClient` and `RestTemplate` instances built from the Spring Boot auto-configured builders, following the stable OpenTelemetry Semantic Conventions for HTTP. The requests are reported with the `http.client.request.duration` metric instead of `http.client.requests`, and with spans named after the request method, such as `GET`, carrying `http.request.method`, `http.response.status_code`, `server.address`, `server.port`, `url.full`, and `error.type` instead of `method`, `status`, `client.name`, `http.url`, and `exception`. The Spring Framework `outcome` and `uri` attributes are kept. When a request fails without a response, `error.type` holds the class name of the I/O error, such as `java.net.ConnectException`, rather than the `ResourceAccessException` wrapping it. The credentials and the values of sensitive query parameters in `url.full` are replaced by `REDACTED`, while the `http.url` attribute used to record the full URL as is. The `arconia.observations.conventions.opentelemetry.http.enabled` property now applies to both HTTP server and client conventions. Learn more about the xref:observability:semantic-conventions/opentelemetry.adoc#_http_client[HTTP Client] conventions.
* The spans of HTTP requests whose response status code signals an error now get the `Error` status also when no exception was thrown, as the OpenTelemetry Semantic Conventions require: `5xx` for HTTP servers, `4xx` and `5xx` for HTTP clients. Learn more about the xref:observability:semantic-conventions/opentelemetry.adoc#_http[HTTP] conventions.
* The OpenTelemetry resource now identifies Arconia as the OpenTelemetry distribution in use, with the stable `telemetry.distro.name` (`arconia-opentelemetry`) and `telemetry.distro.version` attributes. Disable it with `arconia.otel.resource.contributors.distro.enabled=false`. Learn more about the xref:opentelemetry:resource.adoc#_distro_resource_contributor[Distro Resource Contributor].
* The OpenTelemetry resource always declares the schema URL of the OpenTelemetry Semantic Conventions version its attributes follow, also when the OpenTelemetry Semantic Conventions module is not in use. The schema URL is now set by Arconia OpenTelemetry, which contributes the resource attributes it describes.
* The values of the `arconia.otel.resource.attributes` properties are now used as they are, instead of being URL-decoded, consistent with Spring Boot. Previously, a value containing a `%` character prevented the application from starting, and `+` characters were turned into spaces. Only the values of the `OTEL_RESOURCE_ATTRIBUTES` environment variable are percent-decoded, as the OpenTelemetry specification requires.
* The `arconia.otel.resource.enable` properties now work as documented, like the Spring Boot `management.metrics.enable` properties: the longest matching key wins, compared by dot-separated segments, and `all` applies only to the attributes not matched by a more specific key. Previously, a more specific key couldn't re-enable attributes disabled by a shorter one (for example, `process: false` with `process.pid: true` still removed `process.pid`), any other key was ignored when `all` was set, and keys matched partial segments (for example, `host` also matched `hostname`). Learn more about xref:opentelemetry:resource.adoc[OpenTelemetry Resource].
* The process resource contributor now adds `process.creation.time`, which identifies the process together with `process.pid` according to the OpenTelemetry Semantic Conventions, and `process.working_directory`. It no longer reports `process.parent_pid` as `-1` when the process has no parent. Learn more about the xref:opentelemetry:resource.adoc#_process_resource_contributor[Process Resource Contributor].
* The host resource contributor now reports `host.arch` with the values defined by the OpenTelemetry Semantic Conventions, such as `arm64` and `amd64`, instead of the architecture names used by the JVM, such as `aarch64` and `x86_64`. Learn more about the xref:opentelemetry:resource.adoc#_host_resource_contributor[Host Resource Contributor].
* The OS resource contributor now reports `os.description` as the OpenTelemetry Semantic Conventions suggest, like the description reported by `lsb_release` or `ver`, instead of a custom format including the JVM architecture name: on Linux, it's the `PRETTY_NAME` from the `/etc/os-release` file (for example, `Ubuntu 24.04.1 LTS`), while on the other operating systems it's made of the name and version (for example, `Mac OS X 15.6`). It also reports Solaris as `solaris` in `os.type` (the JVM calls it `SunOS`), and detects the OS type independently of the default locale. Learn more about the xref:opentelemetry:resource.adoc#_os_resource_contributor[OS Resource Contributor].
* A new Git resource contributor adds the commit, branch, and repository the application was built from to the OpenTelemetry resource, following the OpenTelemetry Semantic Conventions for version control systems (`vcs.ref.head.revision`, `vcs.ref.head.name`, `vcs.repository.url.full`, and more). It reads the `git.properties` file generated at build time and is disabled by default. Learn more about the xref:opentelemetry:resource.adoc#_git_resource_contributor[Git Resource Contributor].
* The new `arconia.otel.resource.deployment-environment-name` property sets the stable `deployment.environment.name` resource attribute, identifying the deployment environment of the application, such as `production` or `staging`. Learn more about xref:opentelemetry:resource.adoc#_configuration_properties[Configuration Properties].
* When enabled (for example with `arconia.otel.traces.processor.metrics` or `arconia.otel.exporter.otlp.metrics`), the metrics the OpenTelemetry SDK generates about its own processors and exporters now follow the OpenTelemetry Semantic Conventions for SDK metrics, such as `otel.sdk.processor.span.processed` and `otel.sdk.exporter.span.exported`, instead of the legacy names such as `processedSpans` and `queueSize`.
* The Generative AI log events (`arconia.observations.conventions.opentelemetry.ai.inference-content-destination=log-events`) now also work with the OpenTelemetry support provided by Spring Boot, besides Arconia OpenTelemetry.
* The OpenTelemetry documentation now describes the stability of the conventions Arconia follows: which xref:opentelemetry:resource.adoc#_stability[resource attributes] are stable and enabled by default, the xref:observability:semantic-conventions/opentelemetry.adoc#_stability[stability policy] of the OpenTelemetry Semantic Conventions module, and the known deviations from the conventions coming from the Micrometer and xref:observability:semantic-conventions/opentelemetry.adoc#_database[Datasource Micrometer] instrumentation.
