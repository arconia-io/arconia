[what-is-new]
= What's New in Arconia {page-component-version}

Arconia {page-component-version} provides a number of new features and enhancements. This page includes the highlights of the release, but you can also check out the full https://github.com/arconia-io/arconia/releases[release notes] for more details about each new feature and bug fix.

We provide an automated way to upgrade your project to the latest version of Arconia, which is described in the xref:upgrading-arconia.adoc[Upgrading Arconia] documentation.

== Dev Services

=== Core

* The `arconia.dev.services.startup.log-level` has been removed because redundant since Testcontainers already takes care of writing a failed container's logs to the application logs at error level.
* The `reuse` and `shared` properties of each Dev Service have been replaced by a single `reuse-strategy` property, since both answered the same question: whether to use a container that is already running instead of starting a new one. It accepts `framework` (previously `shared=true`), `testcontainers` (previously `reuse=true`), and `none`. The two strategies are mutually exclusive, which removes the cases where an application could discover a container it had started itself. Defaults are unchanged: Dev Services that were shared by default use `framework`, the others use `none`. If you set `shared=false`, use `reuse-strategy=none` instead. If you set `reuse=true`, use `reuse-strategy=testcontainers` instead, keeping in mind that the container is then no longer discoverable by other applications. The old properties are no longer read, and are flagged as removed by the configuration metadata, so your IDE reports them. Learn more about xref:dev-services:index.adoc#_reusing_dev_services[Reusing Dev Services].
* The `framework` reuse strategy is now supported by all the Dev Services. For those where it was not available before (Elasticsearch, Floci, LLDAP, MariaDB, MongoDB, MongoDB Atlas, MySQL, Oracle, Oracle XE, PostgreSQL, Redis), it is opt-in: set `arconia.dev.services.<service-name>.reuse-strategy=framework` to let multiple applications use the same container.
* The container label marking a Dev Service as available to other applications has been renamed from `io.arconia.dev-service.shared` to `io.arconia.dev-service.discoverable`, and is now applied only to discoverable containers, together with the `io.arconia.dev-service.owner` label. As a consequence, applications on this version and applications on the previous one don't discover each other's containers.
* When several containers are available for a Dev Service using the `framework` reuse strategy, the application now tries each of them, oldest first, instead of starting its own container when the oldest one cannot be used.
* A Dev Service running in a container started by another application now reports its links, such as management consoles and telemetry endpoints, both in the startup message and in the `devservices` actuator endpoint. Learn more about xref:dev-services:custom-dev-services.adoc#_exposing_links[Exposing Links].
* The startup message of each Dev Service now reports the container it runs in and, in dev mode, the reuse strategy in effect, including the reason when the configured strategy could not be applied. Learn more about xref:dev-services:index.adoc#_startup_feedback[Startup Feedback].
* The `arconia.dev.services.network.name` property has been removed, and with it the support for a network shared across applications: the shared network is now always isolated per application and is created and removed by Testcontainers. A user-defined `Network` bean remains the way to supply a network with a stable id, for example to combine the shared network with the `testcontainers` reuse strategy. The removed property is flagged by the configuration metadata, so your IDE reports it. Also, every container on the shared network is now reachable by its service name in addition to its `network-aliases`, rather than instead of them. Learn more about xref:dev-services:index.adoc#_shared_network[Shared Network].
* The startup message of a Dev Service now states the container image and whether the container was kept across a Spring Boot DevTools restart, and lists the links the Dev Service exposes on a second line. Learn more about xref:dev-services:index.adoc#_startup_feedback[Startup Feedback].
* When using Spring Boot DevTools, Dev Service containers are kept across restarts in dev mode only. An application that started a container keeps using it across restarts instead of looking for a container started by another application. Changes to the configuration of a Dev Service take effect once the application is stopped and started again. A container that is no longer running is replaced on the next restart. Learn more about xref:dev-services:index.adoc#_lifecycle_management[Lifecycle Management].
* The Dev Services for Elasticsearch, LLDAP, MariaDB, MongoDB, MongoDB Atlas, MySQL, Oracle, Oracle XE, PostgreSQL, and Redis now depend on the Spring Boot module providing the connection details for their service (for example, `spring-boot-jdbc` for the relational databases). The Dev Services no longer declare Spring Boot DevTools as an optional dependency.
* If you build your own Dev Service, the following changes apply. Learn more about xref:dev-services:custom-dev-services.adoc[Building Your Own Dev Service].
** Registering a Dev Service requires declaring its configuration properties with `ServiceSpec.properties()`.
** The container and the discovery are each declared in a single call taking the type and the factory together: `.container(FancyDbContainer.class, () -> new FancyDbContainer(properties))` and `.discovery(FancyDbConnectionDetails.class, container -> ...)`. The `ContainerSpec` and `DiscoverySpec` types have been removed, and the container type must extend `GenericContainer`.
** The `serviceConnectionName(...)` option is set on the service, and `serviceConnection(false)` replaces `serviceConnectionName(null)` for Dev Services with no service connection.
** `SharedDevServicesProperties` has been removed. `BaseDevServicesProperties.isReuse()` has been replaced by `getReuseStrategy()`, and `ContainerConfigurer.reuse(...)` has been renamed to `testcontainersReuse(...)`. A Dev Service that was shared by default declares a `reuseStrategy` property defaulting to `framework`.
** `ResourceMapping` and `VolumeMapping` are now records: use `sourcePath()`, `hostPath()`, and `containerPath()` instead of the getters. A mapping with a blank path is rejected when the properties are bound.
** `DevServiceProvider` has been removed: a Dev Service declares the category of mutually exclusive Dev Services it belongs to when registering, with `category(...)`, and `DevServiceCategories` has moved to the `io.arconia.dev.services.core.registration` package. A conflict is now reported while the Dev Services are registered, before any bean is created.
** `DevServiceLinkProvider` and `DevServiceLinkDefinition` have been removed: a Dev Service declares its links when registering, with `link(label, port)` or `link(label, port, path)`, and they are resolved for a container the application started and for a discovered one alike. `DevServiceLink` no longer has an `id`. Also, and `DevServiceLabels` has moved to the `io.arconia.dev.services.api.registration` package, where `SHARED` is now `DISCOVERABLE`.
** Registering two different Dev Services under the same name fails at startup, and Dev Service names are restricted to lowercase letters, digits, and dashes.
** In the `arconia-dev-services-tests` module, a Dev Service takes part in the discovery test by overriding `createDiscoverableContainer(...)`, which replaces `supportsSharing()` and `createSharedContainer(...)`. `withSharedLabels(...)` is now `withDiscoveryLabels(...)`, and the expected default in `DefaultValues` is set with `reuseStrategy(...)` instead of `shared(...)`.

=== Keycloak

* A new xref:dev-services:keycloak.adoc[Keycloak Dev Service] provides an identity and access management server for development and testing. It configures Spring Security's OAuth2 Client and OAuth2 Resource Server automatically, depending on which is on the classpath, so an application needs no OAuth2 configuration to start logging users in or validating tokens. A realm with a client, roles and users is generated out of the box, and you can configure its users and roles, import your own realms from the classpath or the host filesystem, or turn realm creation off entirely and configure Spring Security yourself.
