[[what-is-new]]
= What's New in Arconia {page-component-version}

Arconia {page-component-version} provides a number of new features and enhancements. This page includes the highlights of the release, but you can also check out the full https://github.com/arconia-io/arconia/releases[release notes] for more details about each new feature and bug fix.

We provide an automated way to upgrade your project to the latest version of Arconia, which is described in the xref:upgrading-arconia.adoc[Upgrading Arconia] documentation.

== Core Features

* The `dev` and `test` profiles activated in the matching bootstrap mode now come from a new `arconia-core-bootstrap-profiles` module, which the Arconia starters and the Arconia Dev Services bring. The `arconia-core-bootstrap` module only detects the mode and has no effect on the application, so that libraries and development tools, such as the Arconia Dev UI, can rely on the mode without changing the profiles of the application. If your project depends on `arconia-core-bootstrap` directly to activate the profiles, depend on `arconia-core-bootstrap-profiles` instead. Learn more about xref:core-features/profiles.adoc[Profiles].
* Arconia now also warns when the profile settings (`arconia.dev.profiles`, `arconia.test.profiles`, `arconia.bootstrap.profiles.enabled`) are found in a configuration tree imported with `spring.config.import=configtree:`, where they have no effect, as it does for configuration files. Learn more about xref:core-features/profiles.adoc#_customizing_the_profiles[Customizing the Profiles].

== Data

* The SQLite dialect for Spring Data JDBC now also stores and reads `ZonedDateTime`, `OffsetTime`, `Year`, `YearMonth`, `java.util.Date`, `java.sql.Timestamp`, `java.sql.Date`, and `java.sql.Time` values. Previously, values of these types could be written, but reading them back failed. Learn more about the xref:data:jdbc-sqlite.adoc#_dates_and_times[SQLite Type Mapping].
* Errors from SQLite are now translated into the matching Spring data access exceptions, such as `DuplicateKeyException` for a violated unique constraint and `CannotAcquireLockException` for a busy database. Previously, they were all reported as `UncategorizedSQLException`. Learn more about xref:data:jdbc-sqlite.adoc#_error_handling[SQLite Error Handling].
* A new `arconia-data-jdbc-sqlite-spring-boot-starter` brings in SQLite support for Spring Data JDBC together with the Spring Boot Starter for Spring Data JDBC, so a single dependency is enough. Learn more about the xref:data:jdbc-sqlite.adoc#_dependencies[SQLite Dependencies].
* The xref:data:jdbc-sqlite.adoc[SQLite documentation] now covers testing, the connection pool, more pragmas, read-only transactions, and dates and times written with `JdbcClient` or `JdbcTemplate`. It also explains that the `transaction_mode=IMMEDIATE` parameter makes reading wait for the current writer too, since Spring Data JDBC runs repository queries in transactions.

== Dev Services

* The observability Dev Services (Grafana LGTM, OpenTelemetry Collector, Phoenix, OpenLIT, and Langfuse) now only start when the application exports the telemetry they receive via OTLP, and the `skip-in-tests` property is removed. In tests, they follow the export of telemetry: they are skipped when it's off, as with the new `arconia-opentelemetry-spring-boot-starter-test`, and start when a test turns it on with the `spring.test.logging.export`, `spring.test.metrics.export`, or `spring.test.tracing.export` properties. If you set `skip-in-tests` to `false`, use those properties instead. Learn more about xref:dev-services:index.adoc#_dev_services_in_test_mode[Dev Services in Test Mode].
* A Dev Service now has a title, which is the name of the product it runs (such as "PostgreSQL"), and an optional description that says what it provides in a sentence. The built-in Dev Services have both. For a custom Dev Service, `title(...)` is now required when registering it, and takes the place of `description(...)`, which is optional and meant for a sentence. The `devservices` actuator endpoint returns both fields. Learn more about xref:dev-services:custom-dev-services.adoc[Custom Dev Services].
* A Dev Service can have a link to its documentation and an icon, which developer tooling such as the Arconia Dev UI shows. The built-in Dev Services link to their page in the Arconia documentation. For a custom Dev Service, set them with `documentation(...)` and `icon(...)` when registering it. The properties of a Dev Service are found from the prefix of its properties class. Learn more about xref:dev-services:custom-dev-services.adoc[Custom Dev Services].
* The name of a custom Dev Service can no longer contain consecutive dashes, such as `fancy--db`. It must contain only lowercase letters, digits, and single dashes between them. Learn more about xref:dev-services:custom-dev-services.adoc[Custom Dev Services].
* The Floci Dev Service now reports the URL of the Floci UI, a web console for the resources in the emulator, among its links. Floci starts the console the first time the URL is opened. Learn more about the xref:dev-services:floci.adoc#_accessing_the_floci_ui[Floci Dev Service].

== Dev UI

* A new Arconia Dev UI gives you a web interface for the application you are developing, served by the application itself in dev mode. Add the new `arconia-dev` dependency, which brings the development tools of Arconia, and open `/a/dev-ui` in your browser. It opens on an Overview of the application, and has pages for its configuration properties, with their values and where they are set, for its environment, and for its Dev Services, with their state, links, and container logs. A console at the bottom of every page shows the logs of the application, across Spring Boot DevTools restarts, and a button in the top bar restarts the application with DevTools. The Dev UI is incubating. Learn more about the xref:dev-ui:index.adoc[Arconia Dev UI].
* With the Arconia Dev UI, a new application no longer answers its first request with the whitelabel error page. In dev mode, a welcome page confirms that the application is running and shows how to add a first endpoint, and a failed request shows the exception at the origin of the failure and its stack trace, with the frames of your application highlighted. The application's own pages and error pages take precedence, and clients asking for JSON are not affected. Learn more about the xref:dev-ui:index.adoc#_welcome_and_error_pages[Welcome and Error Pages].
* The Arconia Dev UI only accepts requests from your own machine, and has no login. Enable remote access for an application that runs in a container, and list the host name of a remote development environment as an allowed host. Its requests are left out of the metrics and traces of the application. Learn more about xref:dev-ui:index.adoc#_accessing_the_dev_ui[Accessing the Dev UI].
* Libraries can contribute their own pages to the Arconia Dev UI by defining a `CardsPage` or `TablePage` bean with the incubating `arconia-dev-ui-api`, without writing any frontend code. Learn more about xref:dev-ui:contributing-pages.adoc[Contributing Pages].

== Docling

* The Docling client can now send a bearer token in the `Authorization` header, which is what a proxy that authenticates the requests to Docling Serve expects. Set it via the `arconia.docling.bearer-token` property, or via `bearerToken()` when building the client with `DoclingServeApi.builder()` or `DoclingServeClient.builder()`. Learn more about the xref:integrations:docling.adoc#_configuration[Docling configuration].
* The Docling Document Reader now processes the sources as a Docling Serve task and waits for it to complete within `arconia.docling.async-timeout` (5 minutes by default), instead of using a synchronous request, which Docling Serve stops after 2 minutes. Learn more about the xref:generative-ai:docling-document-reader.adoc#_ingesting_documents_with_docling[Docling Document Reader].
* The `DocumentMetadata` enumeration of the Docling Document Reader is now `DoclingDocumentMetadata`, so that it no longer clashes with the `DocumentMetadata` enumeration of Spring AI.

== OpenTelemetry

* A new `arconia-opentelemetry-spring-boot-starter-test` turns off the export of logs, metrics, and traces in tests, where there is usually no backend to receive them. Without it, each test logs export failures and closing an application context can take several seconds. It includes the Spring Boot test support for Micrometer metrics and tracing, and adds the same support for logs. The tests that verify the exported telemetry turn it back on with the `spring.test.logging.export`, `spring.test.metrics.export`, and `spring.test.tracing.export` properties. Learn more about xref:opentelemetry:index.adoc#_testing[Testing].
* The exporters now follow the Spring Boot properties that turn the export of a signal on and off: `management.logging.export.enabled`, `management.defaults.metrics.export.enabled`, and `management.tracing.export.enabled`. Previously, they had no effect.
* Arconia now logs a warning at startup when the application sets Spring Boot properties under `+management.opentelemetry.*+` or `+management.otlp.*+`, which have no effect because the `+arconia.otel.*+` properties replace them. Previously, they were silently ignored. Learn more about xref:opentelemetry:index.adoc#_exporting_telemetry[Exporting Telemetry].
* Spans are now tagged with the baggage fields listed in `management.tracing.baggage.tag-fields` also when the baggage arrives with an incoming request. Previously, only the baggage set by the application through the Micrometer Tracing API ended up on spans. Learn more about xref:opentelemetry:traces.adoc#_baggage[Baggage].
* A custom Micrometer Tracing `Propagator` bean now replaces the one Arconia configures, as it does in Spring Boot. Previously, only a custom `OtelPropagator` did, and any other implementation ended up next to the Arconia one.
* Exemplars are now configured with a single property for all the metrics of the application: the Spring Boot `management.tracing.exemplars.include` property, which already applied to the metrics recorded with Micrometer, now also applies to the ones recorded with the OpenTelemetry API. The `arconia.otel.metrics.exemplars.filter` property is removed, and the `OTEL_METRICS_EXEMPLAR_FILTER` environment variable sets the Spring Boot property instead. If you set `arconia.otel.metrics.exemplars.filter`, use `management.tracing.exemplars.include` with `all` instead of `always-on`, `none` instead of `always-off`, and `sampled-traces` instead of `trace-based`. Learn more about xref:opentelemetry:metrics.adoc#_configuration_properties[Metrics Configuration Properties].
* Arconia now stops recording observations, both metrics and traces, for the Spring Boot health endpoint and its `/livez` and `/readyz` probe paths in Servlet applications, so that frequent Kubernetes probes no longer flood the telemetry backend. The observations started while handling those requests, such as the Spring Security or JDBC ones, are skipped too, instead of becoming separate traces. Use `arconia.observations.http.server.additional-ignore-paths` to ignore more paths, or set `arconia.observations.http.server.ignore-paths` to an empty value to observe every request again. Learn more about xref:opentelemetry:instrumentation.adoc#_ignoring_http_server_requests[Ignoring HTTP Server Requests].

== Semantic Conventions

* Setting `arconia.observations.conventions.openinference.ai.base64-image-max-length` to `0` now redacts all base64 media, as in the OpenInference reference implementation. Previously, it removed the limit. Learn more about the xref:observability:semantic-conventions/openinference.adoc#_configuration_properties[OpenInference Configuration Properties].
* The `http.route` attribute and the name of HTTP server spans now include the context path of the application, as the OpenTelemetry Semantic Conventions recommend. For example, with `server.servlet.context-path=/api`, the route `/users/\{id}` is now reported as `/api/users/\{id}`. Learn more about the xref:observability:semantic-conventions/opentelemetry.adoc#_http_server[OpenTelemetry HTTP Server Conventions].
* With the `langsmith` and `openllmetry` flavors of the OpenTelemetry AI Semantic Conventions, the attributes that tell the backend how to display a span, such as `langsmith.span.kind` and `traceloop.span.kind`, are now only recorded on spans. Previously, they were also tags of the metrics, which now have the same tags with every flavor. Learn more about the xref:observability:semantic-conventions/index.adoc[Semantic Conventions].
* With the `openllmetry` flavor, tool executions now record their arguments and result also as `gen_ai.tool.call.arguments` and `gen_ai.tool.call.result`, as the OpenLLMetry instrumentations do. Learn more about the xref:observability:semantic-conventions/openllmetry.adoc[OpenLLMetry Semantic Conventions].

== Testcontainers

* The containers can now be created from an image name given as a string, as in `new PhoenixContainer("arizephoenix/phoenix:latest")`, like the modules of Testcontainers.
* In `PhoenixContainer`, the `GRPC_PORT` constant is now `OTLP_GRPC_PORT` and the `getGrpcPort()` method is now `getOtlpGrpcPort()`, as in `OpenLitContainer`. The new `getOtlpHttpUrl()` and `getOtlpGrpcUrl()` methods return the OTLP endpoints. Learn more about the xref:testcontainers:phoenix.adoc[Phoenix Testcontainers module].
