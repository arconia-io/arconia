[[what-is-new]]
= What's New in Arconia {page-component-version}

Arconia {page-component-version} provides a number of new features and enhancements. This page includes the highlights of the release, but you can also check out the full https://github.com/arconia-io/arconia/releases[release notes] for more details about each new feature and bug fix.

We provide an automated way to upgrade your project to the latest version of Arconia, which is described in the xref:upgrading-arconia.adoc[Upgrading Arconia] documentation.

== Core Features

* The `arconia-core` and `arconia-spring-boot` modules have been reorganized as `arconia-core-annotations`, holding the `@Incubating` and `@Internal` annotations without any Spring Boot dependency, and `arconia-core-bootstrap`, holding the bootstrap mode and profiles. Their packages have been renamed accordingly: `io.arconia.core.support` to `io.arconia.core.annotations`, `io.arconia.boot.bootstrap` to `io.arconia.core.bootstrap`, and `io.arconia.boot.autoconfigure.bootstrap` to `io.arconia.core.bootstrap.autoconfigure`, which includes `BootstrapMode` and `@ConditionalOnDevMode`. The xref:upgrading-arconia.adoc[upgrade recipe] applies the renames.
* When the bootstrap mode is set both as the `arconia.bootstrap.mode` JVM system property and as the `ARCONIA_BOOTSTRAP_MODE` environment variable, the JVM system property now takes precedence, as in the Spring Boot externalized configuration. Previously, the environment variable won, including the one the Arconia CLI sets when running or testing an application. Learn more about the xref:core-features/bootstrap-mode.adoc#_setting_the_bootstrap_mode[Bootstrap Mode].
* The startup message reporting the bootstrap mode and the warnings about misplaced bootstrap properties now appear in the application log. Previously, they were lost because they were logged before the logging system was initialized. A bootstrap mode set in an unsupported location, such as the application configuration, is now also reported when it's set correctly elsewhere too, since that value has no effect.

== Data

* The SQLite dialect for Spring Data JDBC now stores `Instant`, `OffsetDateTime`, `LocalDateTime`, `LocalDate`, and `LocalTime` values as text in the format of the SQLite date and time functions, and reads them back. Previously, reading `Instant`, `OffsetDateTime`, and `LocalDate` values failed. Values written by the application and by SQLite, such as with `CURRENT_TIMESTAMP`, now sort and compare correctly together. Learn more about the xref:data:jdbc-sqlite.adoc#_dates_and_times[SQLite Type Mapping].
* Queries with an offset and no limit now work with SQLite, where they previously failed with a syntax error.
* Calling `JdbcAggregateTemplate.upsert()` with SQLite now fails with an error stating that upserts aren't supported, instead of a syntax error from the database. Learn more about the xref:data:jdbc-sqlite.adoc#_limitations[SQLite Limitations].
* The `SqliteDialect` class has been merged into `JdbcSqliteDialect`. The xref:upgrading-arconia.adoc[upgrade recipe] replaces the references.
* The xref:data:jdbc-sqlite.adoc[SQLite documentation] now covers the recommended connection settings, in-memory databases, schema initialization, deployment, and backups.

== Dev Services

* Test slices now pick up the Dev Service of their technology with no further configuration: `@JdbcTest`, `@DataJdbcTest`, `@DataJpaTest`, and `@JooqTest` for the JDBC Dev Services, `@DataMongoTest`, `@DataRedisTest`, `@DataElasticsearchTest`, and `@DataLdapTest`. For the JDBC slices, the Dev Service replaces the embedded database Spring Boot would otherwise configure; disable the Dev Service for a test with its `enabled` property to get the embedded database back. Learn more on the page of each Dev Service, for example the xref:dev-services:postgresql.adoc#_running_the_application[PostgreSQL Dev Service].
* The observability Dev Services (Grafana LGTM, OpenTelemetry Collector, Phoenix, and OpenLIT) are now skipped in test mode by default, since most tests have no use for a telemetry backend. Set `arconia.dev.services.<service-name>.skip-in-tests` to `false` for the tests that verify the telemetry the application exports. Learn more about xref:dev-services:index.adoc#_dev_services_in_test_mode[Dev Services in Test Mode].
* When the application process exits, the containers it kept across Spring Boot DevTools restarts are now stopped, instead of being left to the Testcontainers resource reaper a few seconds later. Another application can no longer connect to a container that is about to disappear. Containers kept by the `testcontainers` reuse strategy are still left running. Learn more about xref:dev-services:index.adoc#_lifecycle_management[Lifecycle Management].
* The startup message of a Dev Service now includes the host address of its main port, which is what you need to connect a tool on your machine to it, and only mentions the reuse strategy when a container is reused or the configured strategy could not be applied. Learn more about xref:dev-services:index.adoc#_startup_feedback[Startup Feedback].
* The default `startup-timeout` of the Dev Services is now 60 seconds, as in Testcontainers, instead of 30 seconds. The Dev Services that take longer to start keep their 120 seconds default.
* An application connecting to a Dev Service started by another application now honors the configuration set through the `environment` property of the Dev Service, as the application that started it does: the region of Floci, the base DN and password of LLDAP, and the API key of Docling.
* Two Dev Services of the same category, such as two JDBC databases, now fail at startup also when one of them connects to a container started by another application, instead of the second one being silently skipped.
* A new xref:dev-services:index.adoc#_troubleshooting[Troubleshooting] section covers containers that fail to start, running without a container runtime, showing the logs of a container in the application log, and Podman closing idle connections. The documentation also explains how Dev Services work together with xref:dev-services:index.adoc#_spring_boot_docker_compose[Spring Boot Docker Compose], how test application contexts share containers, and how to start containers in parallel.

=== Building Dev Services

The following changes affect the custom Dev Services you build on the Arconia Dev Services API. The xref:upgrading-arconia.adoc[upgrade recipe] applies the renames.

* `BaseDevServicesProperties` has been renamed to `DevServicesProperties`.
* `DevServiceRegistration` and `ContainerInfo` are classes with getters instead of records, so that they can describe more about a Dev Service in the future without breaking changes: `registration.name()` becomes `registration.getName()`, `containerInfo.imageName()` becomes `containerInfo.getImageName()`, and so on. Create instances with their builders. `DevServiceRegistration` also reports the category of the Dev Service, which the `devservices` actuator endpoint now includes.
* `DevServiceSslConfigurer` accepts any Testcontainers `Container`, like `DevServiceContainerCustomizer`.
* `DiscoveredContainer` is a class instead of a record, so that it can carry more information in the future without breaking changes. Its accessors and builder are unchanged.
* The methods of `DevServicesRegistrar` called by Spring are now `final`. Implement `registerDevServices` only.
* A Dev Service auto-configuration only needs to be ordered before Spring Boot's `ServiceConnectionAutoConfiguration`: ordering it after `DevServicesAutoConfiguration` is no longer necessary. Learn more about xref:dev-services:custom-dev-services.adoc[Building Your Own Dev Service].

=== Docling

* The Docling Dev Service now uses the `ghcr.io/docling-project/docling-serve-cpu` image by default, less than half the size of the image with GPU support, which the Dev Service never used.
* The `arconia.dev.services.docling.enable-ui` property has been renamed to `arconia.dev.services.docling.ui-enabled`, consistent with the other boolean properties. The xref:upgrading-arconia.adoc[upgrade recipe] renames it.

=== Elasticsearch

* An application connecting to an Elasticsearch Dev Service started by another application now uses the password configured through the `ELASTIC_PASSWORD` environment variable, as the application that started it does.
* The Elasticsearch Dev Service now runs with a heap of 512 MB to 1 GB (`ES_JAVA_OPTS=-Xms512m -Xmx1g`), instead of the fixed 2 GB Testcontainers configures. Override it through the `environment` property.

=== Grafana LGTM

* A new GenAI dashboard shows the calls to chat and embedding models, their failures and durations, token usage, tool executions, `ChatClient` requests, and the most recent model calls with links to their traces. It's provisioned when the xref:observability:semantic-conventions/opentelemetry.adoc#_generative_ai[OpenTelemetry AI Semantic Conventions] module is on the classpath, whatever the flavor. Learn more about the xref:dev-services:lgtm.adoc#_grafana_dashboards[Grafana Dashboards].
* New HTTP Server and HTTP Client dashboards show the requests handled and sent by the application, with a summary by route or server, traffic and errors by status code, durations, and the most recent failed requests with links to their traces. Each comes in a version for the Micrometer conventions and one for the OpenTelemetry semantic conventions, provisioned according to the conventions the application uses. Learn more about the xref:dev-services:lgtm.adoc#_grafana_dashboards[Grafana Dashboards].
* Prometheus now counts the first value of each metric in rates and totals, such as the first call to an endpoint or a model, which previously only appeared from the second one. Learn more about the xref:dev-services:lgtm.adoc[Grafana LGTM Dev Service].

=== Langfuse

* The new xref:dev-services:langfuse.adoc[Langfuse Dev Service] runs https://langfuse.com[Langfuse] for exploring the traces of AI applications, together with the containers it needs, and sends the traces of the application to it with no configuration. It signs you in to the Langfuse UI as `arconia@example.com` (password `password`), and it's skipped in test mode by default, like the other observability Dev Services.

=== LLDAP

* The LLDAP Dev Service now starts with its default configuration, with the `admin` user and the `password` password. Learn more about the xref:dev-services:lldap.adoc[LLDAP Dev Service].

=== MongoDB

* The MongoDB Dev Service runs a single-node replica set again, so that transactions and change streams work as they do in production.
* The MongoDB Dev Service now starts on Linux kernels 6.19 to 7.0, which MongoDB 8.0 and later refuse to run on with their default memory allocator settings (https://jira.mongodb.org/browse/SERVER-121912[SERVER-121912]).

=== Ollama

* The OpenAI compatibility of the Ollama Dev Service now works with Spring AI 2: the `spring.ai.openai.base-url` property points to the OpenAI-compatible API of Ollama, under `/v1`, where requests previously failed with a 404 error.

=== Keycloak

* The Keycloak Dev Service now imports several realm files, each holding a single realm or a list of realms in the formats Keycloak exports, so that an application with a realm per tenant can run against all of them. The files are configured in `arconia.dev.services.keycloak.realm.import-paths` (replacing the previous `arconia.dev.services.keycloak.realm.import-path` property), and `arconia.dev.services.keycloak.realm.name` selects the realm the application connects to. Learn more about xref:dev-services:keycloak.adoc#_importing_realms[Importing Realms].

== Docling

* The async operations of the Docling client, such as `convertSourceAsync`, now return the result of the task. Previously, they returned an empty response without waiting for the task to complete. They poll the task status as configured by the new `arconia.docling.async-poll-interval` and `arconia.docling.async-timeout` properties, or by the `asyncPollInterval` and `asyncTimeout` options of the client builders, which are no longer ignored. Learn more about the xref:integrations:docling.adoc#_configuration[Docling configuration].
* The auto-configured Docling client now applies the Spring Boot `spring.http.clients.*` settings, such as the SSL bundle and the redirect strategy, so it can connect to a Docling Serve instance whose certificate is signed by a private certificate authority. Previously, only the connect and read timeouts were applied. Learn more about the xref:integrations:docling.adoc#_configuration[Docling configuration].
* Polling the status of a task and clearing the stored results now send the `wait` and `older_then` durations in seconds, as Docling Serve expects.
* The default `arconia.docling.read-timeout` is now 2 minutes instead of 30 seconds, matching the time Docling Serve waits for a synchronous conversion to complete. Previously, converting a document that took longer than 30 seconds failed with a read timeout.
* When logging the requests and responses of the Docling client, the bodies are now truncated to 4000 characters, since a request carries each file as a Base64 string, and the API key and Authorization header values are always fully masked.
* The `API_KEY_HEADER_NAME` constant has moved from `DoclingProperties` to `DoclingServeClient`, next to the client that sends the header. The xref:upgrading-arconia.adoc[upgrade recipe] updates the references.
* The Docling health contributor now backs off when the application defines a `doclingHealthIndicator` or `doclingHealthContributor` bean, as in Spring Boot. Previously, defining a `doclingHealthContributor` bean made the application fail to start. If you replaced the health contributor with a `doclingServeHealthIndicator` or `doclingServeHealthContributor` bean, rename it. The `location` health detail no longer includes the credentials the base URL may carry.
* The `DoclingDocumentReader` now throws an `IllegalStateException` when Docling Serve can't convert one of its sources. Previously, it returned the chunks of the other sources, silently dropping the failed ones. Learn more about xref:generative-ai:docling-document-reader.adoc#_ingesting_documents_with_docling[Ingesting Documents with Docling].
* The `DoclingDocumentReader` no longer asks Docling Serve to include the converted documents in the response, which it didn't use, making the responses several times smaller.
* Combining `files(List)` with `files(Resource...)`, or `urls(List)` with `urls(String...)`, on the `DoclingDocumentReader` builder no longer fails when the list is immutable, and changing a list after building the reader no longer changes the sources it reads.

== Multitenancy

* Tenant resolution is now a chain. The `arconia.multitenancy.resolution.http.resolution-mode` property accepts a list of modes, consulted in order until one resolves a tenant, so that `subdomain, header` reads the tenant from the subdomain when the host matches and from the header otherwise. A custom `HttpRequestTenantResolver` bean still replaces the configured chain, and the new `CompositeHttpRequestTenantResolver` lets it combine custom and built-in resolvers. A resolver may now throw an `InvalidTenantIdentifierException` for input that is present but unusable, which stops the chain. Learn more about xref:multitenancy:web.adoc#_http_tenant_resolution[HTTP Tenant Resolution] and the xref:multitenancy:architecture.adoc[Architecture].
* Tenants can be resolved from the request path with the new `path` mode and a pattern such as `/tenants/\{tenant}/**`, and from the subdomain with the `subdomain` mode and a pattern for the request host such as `\{tenant}.example.com`. Both patterns follow the syntax of Spring MVC request mappings. Learn more about xref:multitenancy:web.adoc#_path_based_resolution[Path-Based Resolution] and xref:multitenancy:web.adoc#_subdomain_based_resolution[Subdomain-Based Resolution].
* The fixed tenant is now a resolution mode. `arconia.multitenancy.resolution.http.resolution-mode=fixed` turns the application into a single-tenant deployment, and `header, fixed` makes the fixed tenant the default tenant for requests without one. The `arconia.multitenancy.resolution.fixed.enabled` property has been removed accordingly. Learn more about xref:multitenancy:web.adoc#_fixed_tenant_and_default_tenant[Fixed Tenant and Default Tenant].
* The tenant identifier policy is configurable with `arconia.multitenancy.identifier.max-length` and `arconia.multitenancy.identifier.pattern`. Learn more about xref:multitenancy:tenant-details.adoc#_tenant_identifier_validation[Tenant Identifier Validation].
* Requests without a usable tenant are handed to a `TenantResolutionFailureHandler`, so that an application can redirect to a tenant selection page or apply its own error conventions instead of the default `application/problem+json` response. Rejections are now logged at `DEBUG` level, and a request carrying the tenant header or cookie more than once is rejected. Learn more about xref:multitenancy:web.adoc#_failure_responses[Failure Responses].
* The core and web modules have a new package layout, with `resolution`, `context` and `tenantdetails` packages replacing the previous `context.resolvers`, `context.events`, `exceptions`, `context.filters` and `context.annotations` packages, and `PropertiesTenantDetailsService` has become `InMemoryTenantDetailsService`. The xref:upgrading-arconia.adoc[upgrade recipe] rewrites imports and the removed property.
* Tenant resolution is stricter and more robust. A blank tenant identifier, such as an empty header or an OAuth2 token with an empty tenant claim, is rejected instead of falling back to the next resolution mode. The default `TenantVerifier` requires the loaded tenant to carry exactly the requested identifier, so a case-insensitive `TenantDetailsService` cannot admit `ACME` as an alias of `acme`. The tenant established for a request is bound again on its asynchronous and error dispatches, CORS preflight requests are no longer rejected, and a tenant registry outage is logged at `WARN` level in a single line. Learn more about xref:multitenancy:web.adoc#_error_dispatches[Error Dispatches].
* The tenant context is propagated to `@Async` methods, `Callable` controller methods, and tasks run by the executors and schedulers auto-configured by Spring Boot, together with the tenant in the logs of those threads. It can be turned off with `arconia.multitenancy.context.propagation.enabled=false`. Learn more about xref:multitenancy:tenant-context.adoc#_context_propagation_across_threads[Context Propagation Across Threads].
* The tenant lookup behind each request's verification can be cached with Caffeine by setting `arconia.multitenancy.details.cache.time-to-live`. Only existing tenants are cached, and the time to live bounds how long a disabled tenant keeps being accepted. Learn more about xref:multitenancy:tenant-details.adoc#_caching_tenant_lookups[Caching Tenant Lookups].
* The JDBC tenant details can be read from a dedicated data source, such as a control-plane database separate from the business data, by annotating it with `@TenantDetailsDataSource`. The web module now also logs at startup when tenants are not verified, which happens silently otherwise, for example when the application has several data sources and none is selected for the tenant details. Learn more about xref:multitenancy:tenant-details.adoc#_dedicated_data_source[Dedicated Data Source].
* The tenant details health indicator has been removed. Spring Boot's `db` health indicator already reports whether the database holding the tenant details can be reached, and a missing tenant details table makes the tenant filter answer with `503 Service Unavailable` and log the cause. The `management.health.tenantdetails.enabled` property no longer has any effect.

== Observability

=== OpenTelemetry

* The OpenTelemetry resource now identifies Arconia as the distribution in use and declares the schema URL of the semantic conventions it follows. Learn more about the xref:opentelemetry:resource.adoc#_distro_resource_contributor[Distro Resource Contributor].
* The new `arconia.otel.resource.deployment-environment-name` property sets the `deployment.environment.name` attribute, such as `production` or `staging`.
* The new Git resource contributor, disabled by default, adds the commit, branch, and repository the application was built from. Learn more about the xref:opentelemetry:resource.adoc#_git_resource_contributor[Git Resource Contributor].
* The resource contributors now report values as the OpenTelemetry Semantic Conventions define them, such as `amd64` instead of `x86_64` for `host.arch`. Learn more about the xref:opentelemetry:resource.adoc#_resource_contributors[Resource Contributors].
* The values of the `arconia.otel.resource.attributes` properties are now used as they are, as in Spring Boot. Previously, a `%` character prevented the application from starting.
* The `arconia.otel.resource.enable` properties now work like Spring Boot's `management.metrics.enable`: the longest matching key wins.
* When enabled, the metrics the OpenTelemetry SDK records about itself use the names of the semantic conventions, such as `otel.sdk.processor.span.processed`.
* `OtlpConnectionDetails` can now provide the headers of the requests to the OTLP endpoint through the new `getHeaders()` method.
* The `OTEL_TRACES_SAMPLER` and `OTEL_TRACES_SAMPLER_ARG` environment variables now configure the sampler. Previously, they were ignored. As the specification requires, the sampler argument only applies to the `traceidratio` and `parentbased_traceidratio` samplers and must be between 0 and 1. Learn more about the xref:opentelemetry:index.adoc#_opentelemetry_environment_variables[OpenTelemetry Environment Variables].
* The OpenTelemetry environment variables now follow the specification more closely. A timeout of `0` means no limit, `OTEL_PROPAGATORS=none` disables the propagation, and values of `OTEL_SDK_DISABLED` other than `true` and `false` are reported and ignored.
* The `OTEL_EXPORTER_OTLP_METRICS_TEMPORALITY_PREFERENCE` and `OTEL_EXPORTER_OTLP_METRICS_DEFAULT_HISTOGRAM_AGGREGATION` environment variables are now supported.
* The warnings about invalid OpenTelemetry environment variables now appear in the application log. Previously, they were lost because they were logged before the logging system was initialized. They never include the values of headers and resource attributes, and a value that isn't correctly percent-encoded is skipped instead of preventing the application from starting. When a value can't be bound, the error names the environment variable it comes from.

=== OpenTelemetry Semantic Conventions

* HTTP client requests made with the `RestClient` and `RestTemplate` built from the Spring Boot auto-configured builders now follow the conventions, and the `http.client.request.duration` metric replaces `http.client.requests`. The `arconia.observations.conventions.opentelemetry.http.enabled` property now covers both HTTP clients and servers. Learn more about the xref:observability:semantic-conventions/opentelemetry.adoc#_http[HTTP] conventions.
* HTTP server requests now get attributes only when their value is available, instead of placeholders such as `UNKNOWN` or `NOT_FOUND` for `http.route`. Requests matching no route have no `http.route`, so filter on the status code instead.
* The URL query string of HTTP server requests is now captured as `url.query` by default, with the values of sensitive parameters replaced by `REDACTED`, as in `url.full` for HTTP clients. The `include-url-query` property has been renamed to `capture-url-query`, and the xref:upgrading-arconia.adoc[upgrade recipe] renames it.
* New properties let you add sensitive query parameters to redact and record selected HTTP headers on the spans. Learn more about the xref:observability:semantic-conventions/opentelemetry.adoc#_http[HTTP] configuration properties.
* HTTP spans now get the `Error` status when the response signals an error, also without an exception.
* Every observation ending in an error now records the stable `error.type` attribute, on both spans and metrics, and successful operations no longer get `error.type=none`. Learn more about xref:observability:semantic-conventions/opentelemetry.adoc#_errors[Errors].
* The `jvm.gc.duration` metric is now exported as a single metric, and the `jvm.threads.live` metric is no longer published, since `jvm.thread.count` replaces it. The JVM dashboard of the Grafana LGTM Dev Service has been updated accordingly. Learn more about the xref:observability:semantic-conventions/opentelemetry.adoc#_jvm[JVM] conventions.
* The documentation now describes the xref:observability:semantic-conventions/opentelemetry.adoc#_stability[stability] of the conventions, their known deviations, and how to enable xref:observability:semantic-conventions/opentelemetry.adoc#_histograms[histogram buckets] to compute percentiles.

=== OpenTelemetry AI Semantic Conventions

==== All Flavors

* Content capturing is now configured by the `capture-message-content`, `capture-tool-definitions`, and `capture-tool-call-content` properties, which every flavor honors. They replace `capture-content`, `include-tool-definitions`, and `include-tool-call-content`, and the xref:upgrading-arconia.adoc[upgrade recipe] migrates them.
* The duration of model calls is now reported with the `gen_ai.client.operation.duration` metric instead of `gen_ai.client.operation`: update the dashboards and alerts using `gen_ai_client_operation_seconds`.
* Spring AI `ChatClient` calls are now reported as agent invocations (`invoke_agent`) instead of `invoke_workflow`.
* Model names are omitted when unknown, instead of being set to `none`, and finish reasons use the well-known values of the conventions, such as `stop`, instead of the provider ones.
* Large media in the captured messages is left out, so that the size of spans and events stays bounded.

==== OpenTelemetry Flavor

* The new `inference-content-destination` property decides where the captured content is recorded: as span attributes (default), in a span event, or in a log event correlated with the span of the model call. Learn more about xref:observability:semantic-conventions/opentelemetry.adoc#_content_capturing[Content Capturing].
* The `OpenTelemetryChatModelEventObservationHandler` now records both span events and log events, and its constructor takes the `OpenTelemetry` instance. The `OpenTelemetryChatClientEventObservationHandler` class has been removed.

==== Langfuse Flavor

* The new `langfuse` flavor sends Spring AI traces to https://langfuse.com[Langfuse]. Learn more about the xref:observability:semantic-conventions/langfuse.adoc[Langfuse Semantic Conventions].

==== LangSmith Flavor

* The `langsmith` flavor now follows the LangSmith SDKs: conversations are grouped into LangSmith threads, and the messages of model and chat client calls are recorded as span attributes instead of span events. Learn more about the xref:observability:semantic-conventions/langsmith.adoc[LangSmith Semantic Conventions].

==== OpenLIT Flavor

* The `openlit` flavor now follows the current OpenLIT SDKs and UI, recording the provider as `gen_ai.provider.name` instead of `gen_ai.system`, and the arguments of tool executions as `gen_ai.tool.call.arguments` instead of `gen_ai.tool.args`. Learn more about the xref:observability:semantic-conventions/openlit.adoc[OpenLIT Semantic Conventions].

==== OpenLLMetry Flavor

* The `openllmetry` flavor now follows the current OpenLLMetry instrumentations, recording the provider as `gen_ai.provider.name` instead of `gen_ai.system`, and grouping conversations into Traceloop sessions. Learn more about the xref:observability:semantic-conventions/openllmetry.adoc[OpenLLMetry Semantic Conventions].

=== OpenInference Semantic Conventions

* Model calls now record their input and output documents, the requested and response models, the cached input tokens, so that Phoenix includes them in the cost, and the available tools. Video and document content, such as PDFs, is also recorded, and the results of parallel tool calls are all recorded instead of only the first one.
* Tool executions now record the tool call ID and the parameters definition of the tool.
* Base64 media longer than `arconia.observations.conventions.openinference.ai.base64-image-max-length` is now redacted, as the OpenInference specification requires, instead of being truncated into an invalid data URI.
* Google GenAI calls are now reported with the OpenInference provider and system values, model names are omitted when unknown, and embedding spans are named `CreateEmbeddings`, as the specification requires.
* The new `hide-llm-tools` property hides the definitions of the tools available to the model.
* The `hide-prompts` and `hide-choices` properties have been removed, together with their environment variables, since they apply to the completions API, which Spring AI doesn't use.
* The documentation now covers sending traces to xref:observability:semantic-conventions/openinference.adoc#_arize_ax[Arize AX].
* The boolean OpenInference environment variables now accept only `true` and `false`, as in the OpenInference reference implementation. Any other value, such as `yes`, is reported in the log and ignored, so the configuration property applies. Previously, it was silently treated as `false`, which overrode a `hide-` property set to `true`. Learn more about the xref:observability:semantic-conventions/openinference.adoc#_environment_variables[Environment Variables].

== Testcontainers

* The Arconia Testcontainers modules now have their own documentation, covering the Langfuse, OpenLIT, Phoenix, and Redis containers. Learn more about xref:testcontainers:index.adoc[Testcontainers].
* The new `arconia-testcontainers-langfuse` module provides `LangfuseContainer`, which runs Langfuse together with the containers it needs. With Arconia OpenTelemetry, tests send traces to it by annotating the container with `@ServiceConnection`. Learn more about xref:testcontainers:langfuse.adoc[Langfuse Testcontainers].
* `PhoenixContainer` now turns off the authentication that Phoenix 21 enables by default, so that Phoenix accepts traces without an API key. Learn more about xref:testcontainers:phoenix.adoc[Phoenix Testcontainers].
* `OpenLitContainer` now requires OpenLIT 2.1.1 or later, the default of the OpenLIT Dev Service, which receives OTLP data with its built-in receiver instead of the OpenTelemetry Collector of the previous versions. Learn more about xref:testcontainers:openlit.adoc[OpenLIT Testcontainers].
* `OpenLitContainer` now keeps the tmpfs mounts configured via `withTmpFs()`, and when it fails to start, it stops its ClickHouse container instead of leaving it running until the JVM exits.
