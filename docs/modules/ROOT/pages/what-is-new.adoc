[[what-is-new]]
= What's New in Arconia {page-component-version}

Arconia {page-component-version} provides a number of new features and enhancements. This page includes the highlights of the release, but you can also check out the full https://github.com/arconia-io/arconia/releases[release notes] for more details about each new feature and bug fix.

We provide an automated way to upgrade your project to the latest version of Arconia, which is described in the xref:upgrading-arconia.adoc[Upgrading Arconia] documentation.

== Dev Services

* Test slices now pick up the Dev Service of their technology with no further configuration: `@JdbcTest`, `@DataJdbcTest`, `@DataJpaTest`, and `@JooqTest` for the JDBC Dev Services, `@DataMongoTest`, `@DataRedisTest`, `@DataElasticsearchTest`, and `@DataLdapTest`. For the JDBC slices, the Dev Service replaces the embedded database Spring Boot would otherwise configure; disable the Dev Service for a test with its `enabled` property to get the embedded database back. Learn more on the page of each Dev Service, for example the xref:dev-services:postgresql.adoc#_running_the_application[PostgreSQL Dev Service].
* The observability Dev Services (Grafana LGTM, OpenTelemetry Collector, Phoenix, and OpenLIT) are now skipped in test mode by default, since most tests have no use for a telemetry backend. Set `arconia.dev.services.<service-name>.skip-in-tests` to `false` for the tests that verify the telemetry the application exports. Learn more about xref:dev-services:index.adoc#_dev_services_in_test_mode[Dev Services in Test Mode].
* When the application process exits, the containers it kept across Spring Boot DevTools restarts are now stopped, instead of being left to the Testcontainers resource reaper a few seconds later. Another application can no longer connect to a container that is about to disappear. Containers kept by the `testcontainers` reuse strategy are still left running. Learn more about xref:dev-services:index.adoc#_lifecycle_management[Lifecycle Management].
* The startup message of a Dev Service now includes the host address of its main port, which is what you need to connect a tool on your machine to it, and only mentions the reuse strategy when a container is reused or the configured strategy could not be applied. Learn more about xref:dev-services:index.adoc#_startup_feedback[Startup Feedback].
* The default `startup-timeout` of the Dev Services is now 60 seconds, as in Testcontainers, instead of 30 seconds. The Dev Services that take longer to start keep their 120 seconds default.
* An application connecting to a Dev Service started by another application now honors the configuration set through the `environment` property of the Dev Service, as the application that started it does: the region of Floci, the base DN and password of LLDAP, and the API key of Docling.
* Two Dev Services of the same category, such as two JDBC databases, now fail at startup also when one of them connects to a container started by another application, instead of the second one being silently skipped.
* A new xref:dev-services:index.adoc#_troubleshooting[Troubleshooting] section covers containers that fail to start, running without a container runtime, showing the logs of a container in the application log, and Podman closing idle connections. The documentation also explains how Dev Services work together with xref:dev-services:index.adoc#_spring_boot_docker_compose[Spring Boot Docker Compose], how test application contexts share containers, and how to start containers in parallel.

=== Building Dev Services

The following changes affect the custom Dev Services you build on the Arconia Dev Services API. The xref:upgrading-arconia.adoc[upgrade recipe] applies the renames.

* `BaseDevServicesProperties` has been renamed to `DevServicesProperties`.
* `DevServiceRegistration` and `ContainerInfo` are classes with getters instead of records, so that they can describe more about a Dev Service in the future without breaking changes: `registration.name()` becomes `registration.getName()`, `containerInfo.imageName()` becomes `containerInfo.getImageName()`, and so on. Create instances with their builders. `DevServiceRegistration` also reports the category of the Dev Service, which the `devservices` actuator endpoint now includes.
* `DevServiceSslConfigurer` accepts any Testcontainers `Container`, like `DevServiceContainerCustomizer`.
* `DiscoveredContainer` is a class instead of a record, so that it can carry more information in the future without breaking changes. Its accessors and builder are unchanged.
* The methods of `DevServicesRegistrar` called by Spring are now `final`. Implement `registerDevServices` only.
* A Dev Service auto-configuration only needs to be ordered before Spring Boot's `ServiceConnectionAutoConfiguration`: ordering it after `DevServicesAutoConfiguration` is no longer necessary. Learn more about xref:dev-services:custom-dev-services.adoc[Building Your Own Dev Service].

=== Docling

* The Docling Dev Service now uses the `ghcr.io/docling-project/docling-serve-cpu` image by default, less than half the size of the image with GPU support, which the Dev Service never used.
* The `arconia.dev.services.docling.enable-ui` property has been renamed to `arconia.dev.services.docling.ui-enabled`, consistent with the other boolean properties. The xref:upgrading-arconia.adoc[upgrade recipe] renames it.

=== Elasticsearch

* An application connecting to an Elasticsearch Dev Service started by another application now uses the password configured through the `ELASTIC_PASSWORD` environment variable, as the application that started it does.
* The Elasticsearch Dev Service now runs with a heap of 512 MB to 1 GB (`ES_JAVA_OPTS=-Xms512m -Xmx1g`), instead of the fixed 2 GB Testcontainers configures. Override it through the `environment` property.

=== LLDAP

* The LLDAP Dev Service now starts with its default configuration, with the `admin` user and the `password` password. Learn more about the xref:dev-services:lldap.adoc[LLDAP Dev Service].

=== MongoDB

* The MongoDB Dev Service runs a single-node replica set again, so that transactions and change streams work as they do in production.
* The MongoDB Dev Service now starts on Linux kernels 6.19 to 7.0, which MongoDB 8.0 and later refuse to run on with their default memory allocator settings (https://jira.mongodb.org/browse/SERVER-121912[SERVER-121912]).

=== Ollama

* The OpenAI compatibility of the Ollama Dev Service now works with Spring AI 2: the `spring.ai.openai.base-url` property points to the OpenAI-compatible API of Ollama, under `/v1`, where requests previously failed with a 404 error.

=== Keycloak

* The Keycloak Dev Service now imports several realm files, each holding a single realm or a list of realms in the formats Keycloak exports, so that an application with a realm per tenant can run against all of them. The files are configured in `arconia.dev.services.keycloak.realm.import-paths` (replacing the previous `arconia.dev.services.keycloak.realm.import-path` property), and `arconia.dev.services.keycloak.realm.name` selects the realm the application connects to. Learn more about xref:dev-services:keycloak.adoc#_importing_realms[Importing Realms].

== Multitenancy

* Tenant resolution is now a chain. The `arconia.multitenancy.resolution.http.resolution-mode` property accepts a list of modes, consulted in order until one resolves a tenant, so that `subdomain, header` reads the tenant from the subdomain when the host matches and from the header otherwise. A custom `HttpRequestTenantResolver` bean still replaces the configured chain, and the new `CompositeHttpRequestTenantResolver` lets it combine custom and built-in resolvers. A resolver may now throw an `InvalidTenantIdentifierException` for input that is present but unusable, which stops the chain. Learn more about xref:multitenancy:web.adoc#_http_tenant_resolution[HTTP Tenant Resolution] and the xref:multitenancy:architecture.adoc[Architecture].
* Tenants can be resolved from the request path with the new `path` mode and a pattern such as `/tenants/{tenant}/**`, and from the subdomain with the `subdomain` mode and a pattern for the request host such as `{tenant}.example.com`. Both patterns follow the syntax of Spring MVC request mappings. Learn more about xref:multitenancy:web.adoc#_path_based_resolution[Path-Based Resolution] and xref:multitenancy:web.adoc#_subdomain_based_resolution[Subdomain-Based Resolution].
* The fixed tenant is now a resolution mode. `arconia.multitenancy.resolution.http.resolution-mode=fixed` turns the application into a single-tenant deployment, and `header, fixed` makes the fixed tenant the default tenant for requests without one. The `arconia.multitenancy.resolution.fixed.enabled` property has been removed accordingly. Learn more about xref:multitenancy:web.adoc#_fixed_tenant_and_default_tenant[Fixed Tenant and Default Tenant].
* The tenant identifier policy is configurable with `arconia.multitenancy.identifier.max-length` and `arconia.multitenancy.identifier.pattern`. Learn more about xref:multitenancy:tenant-details.adoc#_tenant_identifier_validation[Tenant Identifier Validation].
* Requests without a usable tenant are handed to a `TenantResolutionFailureHandler`, so that an application can redirect to a tenant selection page or apply its own error conventions instead of the default `application/problem+json` response. Rejections are now logged at `DEBUG` level, and a request carrying the tenant header or cookie more than once is rejected. Learn more about xref:multitenancy:web.adoc#_failure_responses[Failure Responses].
* The core and web modules have a new package layout, with `resolution`, `context` and `tenantdetails` packages replacing the previous `context.resolvers`, `context.events`, `exceptions`, `context.filters` and `context.annotations` packages, and `PropertiesTenantDetailsService` has become `InMemoryTenantDetailsService`. The xref:upgrading-arconia.adoc[upgrade recipe] rewrites imports and the removed property.
* The tenant details health indicator has been removed. Spring Boot's `db` health indicator already reports whether the database holding the tenant details can be reached, and a missing tenant details table makes the tenant filter answer with `503 Service Unavailable` and log the cause. The `management.health.tenantdetails.enabled` property no longer has any effect.

== Observability

=== OpenTelemetry

* The OpenTelemetry resource now identifies Arconia as the distribution in use (`telemetry.distro.name` and `telemetry.distro.version`) and always declares the schema URL of the semantic conventions its attributes follow. Learn more about the xref:opentelemetry:resource.adoc#_distro_resource_contributor[Distro Resource Contributor].
* The new `arconia.otel.resource.deployment-environment-name` property sets the `deployment.environment.name` attribute, such as `production` or `staging`.
* A new Git resource contributor, disabled by default, adds the commit, branch, and repository the application was built from (`vcs.*` attributes), read from the `git.properties` file. Learn more about the xref:opentelemetry:resource.adoc#_git_resource_contributor[Git Resource Contributor].
* The resource contributors report values as the OpenTelemetry Semantic Conventions define them. `host.arch` uses values such as `arm64` and `amd64` instead of the JVM ones (`aarch64`, `x86_64`). `os.description` reads like the output of `lsb_release` (on Linux, the `PRETTY_NAME` of `/etc/os-release`, such as `Ubuntu 24.04.1 LTS`), and `os.type` reports Solaris as `solaris`. The process contributor adds `process.creation.time` and `process.working_directory`, and omits `process.parent_pid` when the process has no parent. Learn more about the xref:opentelemetry:resource.adoc#_resource_contributors[Resource Contributors].
* The values of the `arconia.otel.resource.attributes` properties are now used as they are, as in Spring Boot, and only the `OTEL_RESOURCE_ATTRIBUTES` environment variable is percent-decoded. Previously, a `%` character prevented the application from starting, and `+` characters became spaces.
* The `arconia.otel.resource.enable` properties now work as documented, like Spring Boot's `management.metrics.enable`: the longest matching key wins, compared by dot-separated segments, and `all` covers only the attributes no other key matches.
* When enabled, the metrics the OpenTelemetry SDK records about its processors and exporters use the names of the semantic conventions, such as `otel.sdk.processor.span.processed`, instead of legacy names such as `processedSpans`.

=== OpenTelemetry Semantic Conventions

* HTTP client requests made with the `RestClient` and `RestTemplate` built from the Spring Boot auto-configured builders now follow the OpenTelemetry Semantic Conventions. The `http.client.request.duration` metric replaces `http.client.requests`, spans are named after the request method, and `http.request.method`, `http.response.status_code`, `server.address`, `server.port`, `url.full`, and `error.type` replace `method`, `status`, `client.name`, `http.url`, and `exception`, while `outcome` and `uri` are kept. Credentials and sensitive query parameters are redacted in `url.full`. The `arconia.observations.conventions.opentelemetry.http.enabled` property now covers both HTTP clients and servers. Learn more about the xref:observability:semantic-conventions/opentelemetry.adoc#_http_client[HTTP Client] conventions.
* HTTP server requests now get attributes only when their value is available, instead of placeholders such as `UNKNOWN`, `NOT_FOUND`, or `REDIRECTION` for `http.route`: requests matching no route have no `http.route`, so filter on the status code instead (for example, `http_route="", http_response_status_code="404"` in PromQL). The root route is `/`, `http.request.method_original` is recorded only for methods reported as `_OTHER`, and HTTP/2 and HTTP/3 are reported as `network.protocol.version` `2` and `3`.
* `CONNECT` and `QUERY` requests are now reported with their method instead of `_OTHER`, by both the HTTP server and client conventions.
* The URL query string of HTTP server requests is now captured as `url.query` by default, as the conventions require, with the values of sensitive parameters, such as the signatures of pre-signed cloud storage URLs, replaced by `REDACTED`. The parameters are configurable with `arconia.observations.conventions.opentelemetry.http.sensitive-query-parameters`. The `include-url-query` property has been renamed to `capture-url-query`, and the xref:upgrading-arconia.adoc[upgrade recipe] renames it.
* HTTP spans now get the `Error` status when the response signals an error, also without an exception: `5xx` for servers, `4xx` and `5xx` for clients.
* Every observation ending in an error now records the stable `error.type` attribute, on both spans and metrics: the status code for HTTP error responses, otherwise the canonical class name of the error. For HTTP client requests failing without a response, it's the I/O error, such as `java.net.ConnectException`, rather than the `ResourceAccessException` wrapping it. Successful operations no longer get `error.type=none`. Disable it with `arconia.observations.conventions.opentelemetry.error.enabled=false`. Learn more about xref:observability:semantic-conventions/opentelemetry.adoc#_errors[Errors].
* The `jvm.gc.duration` metric is now exported as a single metric, instead of one for GC pauses and one for concurrent phases. The `jvm.threads.live` metric is no longer published, since `jvm.thread.count` replaces it: use `sum(jvm_thread_count_threads)` in Prometheus. The JVM dashboard of the Grafana LGTM Dev Service has been updated accordingly.
* The documentation now describes the xref:observability:semantic-conventions/opentelemetry.adoc#_stability[stability] of the conventions and of the xref:opentelemetry:resource.adoc#_stability[resource attributes], the known deviations coming from Micrometer, Datasource Micrometer, and Spring AI, and how to enable xref:observability:semantic-conventions/opentelemetry.adoc#_histograms[histogram buckets] to compute percentiles.

=== OpenTelemetry AI Semantic Conventions

* Content capturing is now configured by three switches that every flavor honors: `arconia.observations.conventions.opentelemetry.ai.capture-message-content`, `capture-tool-definitions`, and `capture-tool-call-content`. They replace `capture-content`, `include-tool-definitions`, and `include-tool-call-content`, some values of which were silently ignored by some flavors, and the xref:upgrading-arconia.adoc[upgrade recipe] migrates them.
* With the `opentelemetry` flavor, the new `inference-content-destination` property decides where the captured messages and tool definitions are recorded: as span attributes (default), in a span event, or in a `gen_ai.client.inference.operation.details` log event, structured and correlated with the span of the model call. Log events also work with the OpenTelemetry support of Spring Boot. Learn more about xref:observability:semantic-conventions/opentelemetry.adoc#_content_capturing[Content Capturing].
* Spring AI `ChatClient` calls are now reported as agent invocations (`invoke_agent`) instead of `invoke_workflow`, with `gen_ai.request.model` when the prompt options set it. The streaming flag moves back to Spring AI's `spring.ai.chat.client.stream` attribute. The `OpenTelemetryChatClientEventObservationHandler` has been removed: the messages of a chat client call are recorded on its span only with the `span-attributes` destination.
* The duration of model calls is now reported with the `gen_ai.client.operation.duration` metric instead of `gen_ai.client.operation`, for all flavors: update the dashboards and alerts using `gen_ai_client_operation_seconds`.
* Model names are omitted when unknown, instead of being set to `none`. Finish reasons use the well-known values of the conventions (`stop`, `length`, `content_filter`, `tool_call`, `error`) instead of the provider ones, such as `STOP` (OpenAI) or `end_turn` (Anthropic), and captured output messages always include one.
* The `openlit` flavor now follows the current OpenLIT SDKs and UI: the provider is recorded as `gen_ai.provider.name` instead of `gen_ai.system`, with `gcp.vertex_ai` instead of `vertex_ai` for Vertex AI, and the arguments of tool executions as `gen_ai.tool.call.arguments` instead of `gen_ai.tool.args`, so the OpenLIT UI shows them in the tool call view. The `OpenLitToolCallingObservationConvention` and `OpenLitAdvisorObservationConvention` classes have been removed, since the flavor now uses the OpenTelemetry conventions for tool executions and advisors.
* The `langsmith` flavor now follows the LangSmith SDKs. The conversation ID of the chat memory is recorded as the `thread_id` metadata, so LangSmith groups the traces of a conversation into a thread, instead of `langsmith.trace.session_id`, which identifies the LangSmith project. The messages of model and chat client calls are recorded as the `gen_ai.prompt` and `gen_ai.completion` span attributes instead of span events, so the earlier assistant and tool messages of a conversation appear among the inputs of the call rather than its outputs. Image model calls get the `llm` run type and `gen_ai.system`, Google GenAI is reported as `google`, and cached input tokens are recorded as numbers. The `LangSmithChatClientObservationHandler` class has been removed, and `LangSmithChatModelObservationHandler` has no constructor arguments any more.
* The `openllmetry` flavor now follows the current OpenLLMetry instrumentations, which adopted the OpenTelemetry Semantic Conventions for Generative AI: the provider is recorded as `gen_ai.provider.name` instead of `gen_ai.system`. The conversation ID of the chat memory is also recorded as the `session_id` association property (`traceloop.association.properties.session_id`). The `OpenLLMetryEmbeddingModelObservationConvention` class has been removed, since the flavor now uses the OpenTelemetry conventions for embedding models.

=== OpenInference Semantic Conventions

* Google GenAI calls now get `google` as `llm.provider` and `vertexai` as `llm.system`, instead of the `google_genai` value from Spring AI.
* Base64 images longer than `arconia.observations.conventions.openinference.ai.base64-image-max-length` are now redacted, as the OpenInference specification requires, instead of being truncated into an invalid data URI.
* The results of parallel tool calls are now all recorded, each as a separate input message with its `message.tool_call_id` and `message.name`, instead of only the first one.
* Model names are omitted when unknown, instead of being set to `none`. The output of a tool execution is recorded with the `text/plain` MIME type unless it's JSON, and omitted when the tool returns no result.
* The `OPENINFERENCE_*` environment variables now take effect. They were mapped to properties that the OpenInference configuration didn't read.
* Model calls now record the `input.value` and `output.value` JSON documents with their MIME types, the requested and response models (`llm.request.model_name`, `llm.response.model_name`), the cached input tokens as numbers (`llm.token_count.prompt_details.cache_read`, `llm.token_count.prompt_details.cache_write`), so that Phoenix includes them in the cost, and the name and description of each available tool (`llm.tools.<index>.tool.name`, `llm.tools.<index>.tool.description`). Audio content gets its MIME type.
* Tool executions now record the tool call ID (`tool.id`) and the parameters definition of the tool (`tool.parameters`).
* The new `arconia.observations.conventions.openinference.ai.hide-llm-tools` property, also set with the `OPENINFERENCE_HIDE_LLM_TOOLS` environment variable, hides the definitions of the tools available to the model.
